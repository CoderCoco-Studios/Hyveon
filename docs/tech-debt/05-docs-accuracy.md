# 05 — Docs-site and OpenSpec accuracy

## Summary

All 23 pages under `docs/docs/**` were audited claim-by-claim against the code at `f5e16ab0`; 19 carry at least one factually wrong statement, and only `install.md`, `app/index.md` and (behaviourally) `app/costs.md` / `app/audit.md` come through essentially clean. The dominant pattern is **enumeration rot**: a sixth Lambda package (`health-check`) and a second conditional function landed in PRs #491–#530 and were documented on `components/lambdas.md` and `components/infra.md` only — the count "five Lambda packages, four always-on" is still wrong in nine other places including `CLAUDE.md` itself, and the same shape repeats for DynamoDB tables (2 vs "three"), Secrets Manager secrets (3 vs "two"), cloud-provider DI tokens (7 vs "six"), controllers (13 vs 12 table rows), and npm-script chains that gained an `app:build:lambdas` step nobody propagated. The second pattern is **screenshot rot**: every PNG under `docs/static/img/app/` was captured 2026-08-04..09, before the custom title bar, Cloud Health section, auto-update controls, diagnostics export, port visibility and health-check wizard fields shipped — so the imagery contradicts the prose on at least eight pages. OpenSpec is in better shape than the site: 5 of the 32 capability specs have a stale requirement, but two shipped capabilities (`game-health-checks`, `release-automation`) have **no spec at all** because three completed changes were never synced or archived. Total remediation ≈ 4–5 days across 10 PRs, most of it mechanical.

## Rules to add or update

**1. `.claude/rules/docs-enumerations.md` (new).**
> When a change adds or removes a Lambda package, an infra resource kind, a DynamoDB table, a Secrets Manager secret, a Nest controller, a DI token, or an npm script, grep the whole repo — `CLAUDE.md`, `docs/docs/**`, `openspec/specs/**`, and TSDoc comments — for the *old count word* ("five", "three", "six") and for the old list, and update every hit in the same PR. Counts are the single most repeated fact in this repo and the single most frequently wrong one.

*Why:* nine of the twelve highest-impact findings in this report are one PR's uncounted sixth Lambda propagating into `CLAUDE.md`, four docs pages, one OpenSpec spec, and two source comments.

**2. `scripts/check-docs-references.mjs` + a `docs-refs` CI job (new).** A mechanical checker cannot judge prose, but it can catch the classes of error that dominate section E:
- every backticked path in `docs/docs/**` and `CLAUDE.md` that looks like a repo path (`app/…`, `docs/…`, `.github/…`, `openspec/…`) must exist on disk;
- every backticked `npm run <script>` must exist in the relevant `package.json`;
- every `/img/**` and `/diagrams/**` reference must resolve under `docs/static/`;
- every backticked string matching an IPC-channel shape (`^[a-z][a-zA-Z]*(\.[a-zA-Z]+)+$`) must appear as a `@MessagePattern` argument somewhere in `app/packages/desktop-main/src/controllers/`.
Run it from `.github/workflows/docs-build.yml` (which already triggers on `docs/**`) *and* extend that workflow's `paths` to include `app/packages/desktop-main/src/controllers/**` and `package.json`, so a code-side rename fails the docs job rather than silently rotting a page. Exit non-zero with `file:line` for each miss. Estimated build: M.

**3. `.claude/rules/worktree.md` sibling — screenshot freshness.** Add to the `write-docs` skill (and `openspec/specs/docs-screenshot-capture/spec.md`) a requirement that any PR changing `app/packages/web/src/pages/**` or `app/packages/web/src/components/app-layout.component.tsx` either re-runs `npm run docs:screenshots` or states in the PR body why the affected images are unaffected. The existing spec covers *how* to capture but has no requirement tying captures to UI changes, which is why 18 images are two-plus weeks behind the UI.

**4. CLAUDE.md "docs in the same PR" — compliance measurement.** Sampling the 13 most recent behaviour-changing merges to `main` (#524–#538, excluding the hooks-only #523):

| Type | Sample | Touched `docs/docs/**` | Rate |
|---|---|---|---|
| `feat` | #538, #531, #529, #530, #528, #526, #524 | 7 | **7/7 (100%)** |
| `fix` | #537, #536, #534, #535, #525, #527 | 1 (#537) | **1/6 (17%)** |

The rule is being followed for features and effectively ignored for fixes — and three of the five non-compliant fixes were operator-visible (#525 removed the File/Edit/View menu bar, #536/#534 changed how log lines render). Proposed amendment to `CLAUDE.md`'s "Before opening a PR" section:
> The docs obligation applies to `fix:` PRs on exactly the same terms as `feat:`. If a fix changes anything an operator can see — a rendered value, a control, a message, a default — the page that documents it is updated in the same PR. If it changes nothing operator-visible, say so in the PR body in one line. "It's only a bug fix" is not an exemption.

**5. `.claude/rules/spec-driven-development.md` — add an exit gate.** A change whose `tasks.md` is fully checked and whose code is merged MUST be `/opsx:sync`'d and `/opsx:archive`d before the next change in the same capability area is proposed. ## Bugs found incidentally

**Bug 1 — the health-check Lambda bundle is missing from packaged builds.** `electron-builder.yml:224-235` ships exactly five lambda `dist/` directories via `extraResources`, and its own comment says "must stay in sync with the five `@hyveon/lambda-*` packages". `app/packages/lambda/health-check` is not among them, even though `app/package.json:8` (`build:lambdas`) builds it and `app/packages/infra/src/lambdas.ts:674` deploys it whenever any game declares a `healthCheck`. `PulumiService.getLambdaBundlesDir()` resolves to `<resourcesPath>/lambda` in a packaged app, so an operator running the installed build who configures a health check will fail the apply on a missing `handler.cjs` — the same class of failure as PR #465. Fix: add the sixth `from`/`to` pair and update the comment. This is invisible in dev because dev resolves bundles from the source tree.

**Bug 2 — `iam:SimulatePrincipalPolicy` is granted nowhere.** `IamCheckService` sends `SimulatePrincipalPolicyCommand` (`app/packages/desktop-main/src/services/IamCheckService.ts:3`) against the deploy user's own ARN, but `HYVEON_DEPLOY_ALL_STATEMENTS` scopes `iam:*` to `arn:aws:iam::*:role/hyveon-*` and `arn:aws:iam::*:policy/hyveon-*` (`app/packages/shared/src/iamPolicy.ts:101-105`) — the user ARN matches neither, and no other statement grants the action. Both the guided-IAM and manual paths should therefore get `AccessDenied` from the wizard's own permission check. It is advisory/non-blocking so the wizard degrades rather than breaks, which is presumably why it has gone unnoticed. Fix: add a statement granting `iam:SimulatePrincipalPolicy` on `arn:aws:iam::*:user/*` (or the deploy user specifically) to both `docs/docs/setup.md`'s policy block and `iamPolicy.ts` — `iamPolicy.test.ts` locks the two together, so they must move in one commit.

## Method

Fanned out to 13 read-only sub-agents, all on `model: "opus"` because every task here is a judgment call about whether a sentence is true. Split: 10 `docs-accuracy-auditor` runs covering all 23 pages (one per long page — `architecture`, `setup`, `management-app`, `infra`, `lambdas`, `integration-tests` — and one per small group elsewhere), each told explicitly to treat the whole page as changed rather than diff-scoped; 2 `docs-coverage-auditor` runs for the missing direction (desktop-main + web; infra + lambdas + shared + cloud-aws); and 3 further `docs-accuracy-auditor` runs repurposed to audit `openspec/specs/**` in batches of 6–8 capabilities. Concurrency was capped repo-wide at 20 agents shared with the other four audit areas, so the batches were trickled rather than run in one wave. I handled the `openspec/changes/**` classification, the archive sweep, the screenshot-freshness dating (`git log` per PNG), the CLAUDE.md compliance sample, and all spot-checking directly. Every `file:line` in this report was re-verified by hand or by targeted `grep`/`sed` before inclusion; nothing an agent asserted was carried through unchecked. **Not covered:** the 31 archived changes were given a checkbox-count pass only, not a per-task implementation audit; the 20 OpenSpec specs outside the three staleness batches (`aws-credentials`, `cloud-bootstrap`, `guided-iam-provisioning`, `iac-*`, `node-toolchain-version`, `app-icon`, `install-and-signing-docs`, `orchestrator-integration-coverage`, `guided-region-selection`, `cost-visibility` partial) were not read line-by-line; and `docs/diagrams/*.d2` sources were checked only for the existence of their rendered SVGs, not for whether each diagram's content still matches the architecture it depicts.
