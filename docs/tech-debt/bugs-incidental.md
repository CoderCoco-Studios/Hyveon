## Suggested handling

Give their own `fix(...)` PR before the cleanup stacks start: bug 1 (packaged-app lambda dist omission — silent apply failure for any operator with a health check), bug 2 (Discord Client-ID wipe — silent data loss on a routine token-rotation save), and bug 4 (StrictMode `mountedRef` never re-armed — hangs the settings form in every dev session). All three are small, self-contained, and independently testable; bundling them into an unrelated cleanup PR would bury a real regression fix in a large diff.

Bug 3 (missing `iam:SimulatePrincipalPolicy` grant) is also worth a dedicated fix since it's a wrong-IAM-scope defect, but touches `docs/docs/setup.md` and `iamPolicy.ts` together per the existing test lock — keep it a one-commit PR, not folded into report 05's broader docs-accuracy pass.

Everything in **Severity: low** can ride along in whichever report's cleanup PR already touches that file (e.g. bug 5's StrictMode guard lands with report 01's wizard-step consolidation; bugs 25-26 land with report 02's doc-comment pass). **Process/tooling** items (38-43) are configuration/comment fixes with no runtime risk — batch them into one small chore PR alongside report 04's instruction-drift fixes, except bug 43 (spike removal) which is a real behavior change and needs its own PR with e2e verification.
