# 03 — Duplicated and over-complex logic

## Summary

The repo has one dominant duplication pattern and one dominant complexity pattern. The duplication pattern is **"the same unit written twice, once for the game variant and once for the Lambda/infra variant"** — exactly what the owner flagged in PR #538 ("seeing some duplication between the lambda and non lambda get log calls. Can we extract common functionality out into shared class functions?") and PR #537 ("this block ended up byte-for-byte identical … across three call sites"). PR #538 fixed that pattern *inside* `LogsService` but left the identical pairing in `logs.controller.ts` and `preload.ts` untouched, and the same shape recurs across `desktop-main`, the five Lambdas, `cloud-aws`, and the two log pages. The complexity pattern is a handful of files that absorbed everything: `PulumiService.ts` at 6100 lines with a 1130-line `apply`, `iac.controller.ts` at 1721 lines, `hyveon-api.ts` at 2452, and three React components carrying 25–34 `useState` calls each.

Three mechanical duplications dominate by raw count: `err instanceof Error ? err.message : String(err)` appears **189 times** in non-test source with no shared helper (four private re-implementations of that helper already exist); the cached-AWS-client "rebuild if region or credentials signature changed" block appears **12 times** across two packages; and `app/packages/web/src/api.service.ts` carries **24 type declarations hand-copied from `@hyveon/shared`**, each annotated "keep this copy in sync with it", in a package that already depends on shared. A distinct and cheaper category is **helpers that already exist and are simply not used** — `resolveDefaultAwsRegion` (rewritten 9 times), `sleep()` (rewritten in `LogsService`), `launchElectron()` (bypassed at 15 e2e sites), `ui/select.component.tsx` (imported by exactly one file while 10 raw `<select>`s exist), and `test-mock-registry.ts` (documented as *the* jsdom mock seam, imported only by its own spec while 16 files hand-roll `vi.stubGlobal('hyveon', …)` 60 times).

Test code is worse per-line than production code: the seven `PulumiService.*.test.ts` files each redefine the same ten `makeX()` factories, 59 spec files hand-roll a byte-identical winston logger mock, 10 files redeclare `PATTERN_METADATA_KEY` to back 66 near-identical assertions, and 10 files hand-maintain a full `StackOutputs` literal — a type with no optional fields, so adding one field breaks all ten at once.

Rough total: **73 findings**, ~**18 PRs**, ~**18–22 working days** if all are taken. The nine S-effort items cover roughly a third of the raw occurrence count for about two days of work. Nothing here is machine-enforced — `app/eslint.config.js` has no `sonarjs`, `complexity`, `max-lines`, or duplicate-detection rule, and deliberately stays on the non-type-checked preset.

**Three areas were checked and found already clean**, and are called out so nobody re-audits them: `infra/src/iam.ts` at the statement level (already has `assumeRolePolicyForService:300`, `LAMBDA_ASSUME_ROLE_POLICY:308`, `logStatement:320`, and a VPC-statement factory); resource tagging (one `DEFAULT_TAGS` at `program.ts:174` applied as a provider `defaultTags`, not repeated per resource); and the Playwright e2e **structure** (page objects under `web/e2e/pages/`, shared fixtures under `web/e2e/fixtures/`, one Nest DI harness at `ipc-harness.ts` — no spec calls `Test.createTestingModule` directly).

**One agent finding was investigated and dropped as a false positive.** CodeRabbit's PR #514 comment — "Use `renderPage()` for the component tests. Direct `render()` calls bypass the required web test setup" — is factually wrong and there is no violation set. All 12 routed-page specs already use `renderPage()`; the other 37 specs are non-routed component specs, for which bare `render()` is the documented correct call (`test-utils/render-page.utils.tsx:27`: "For per-component tests that don't depend on the providers, render the component directly instead"), and the "required setup" (jest-dom matchers + `afterEach(cleanup)`) is wired globally via `app/vitest.setup.ts`, not by `renderPage()`. The real problem underneath that comment is finding 55.

## Rules to add or update

**1. New file `.claude/rules/duplication.md` — "The second copy is the review gate."**

> When you write a method, component, or resource block that differs from an existing one only by an identifier, a channel prefix, or a resolved name, extract the shared body **before** opening the PR — do not wait for a reviewer to ask. The house standard is already on record: PR #538 ("seeing some duplication between the lambda and non lambda get log calls. Can we extract common functionality out into shared class functions?") and PR #537 ("byte-for-byte identical … across three call sites"). Threshold: **≥3 occurrences, or ≥2 with a non-trivial body**. Name the extraction in the PR body so the reviewer can check it rather than find it.
>
> Corollary: when you extract, extract at **every** layer the pair crosses. PR #538 fixed `LogsService` but left the identical pair in `logs.controller.ts` and `preload.ts` — the duplication survived the review meant to kill it.
>
> Second corollary: if you find yourself writing a comment that says "mirrors X", "duplicates X", or "keep this copy in sync with X", stop. That comment is the bug report. There are currently **65 such comments in `hyveon-api.ts` alone**, 24 more in `api.service.ts`, and about a dozen in `desktop-main/src/services` — each sitting on top of a real duplication.

Why: this is the single most-repeated review comment in the last 40 merged PRs, and the fix is always cheaper before the diff is written than after.

**2. Add to `.claude/rules/typescript-conventions.md` — check for the existing helper first.**

> Before writing a small utility (error normalization, `sleep`, an env accessor, a type guard, a region resolver, a UI primitive), grep `app/packages/shared/src/index.ts` and the target package's own `lib` / `ui` / `test-utils` / `services` directory for an existing one.

Why: `resolveDefaultAwsRegion` existed and was hand-rewritten 9 times; `sleep()` existed and was rewritten in `LogsService`; `errMessage` was privately re-implemented four times; `ui/select.component.tsx` exists and 10 raw `<select>`s were written anyway; `launchElectron()` exists and 15 e2e sites hand-rolled it.

**3. Add to `.claude/rules/testing-conventions.md` — fixtures over per-spec scaffolding, and the `renderPage()` scope.**

> When three or more spec files need the same stub factory, mock module, or config literal, put it in the package's fixture module (`infra/src/testing/fixtures.ts` and `desktop-main/src/services/__fixtures__/` are the existing pattern) rather than copying the factory. Any type with no optional fields (`StackOutputs`, `DeploymentConfig`) **must** be constructed through a fixture builder in tests, never as an inline literal — otherwise adding one field breaks every spec at once.
>
> `renderPage()` is for **routed-page specs only**. Per-component specs render directly — that is the documented contract at `render-page.utils.tsx:27`, and all 12 page specs already comply. Do not accept review suggestions to widen it.

Why: ~1200 lines of duplicated scaffolding across the seven `PulumiService.*.test.ts` files, 59 copies of the same logger mock, 10 hand-maintained `StackOutputs` literals. The last clause pre-empts a recurring over-broad bot suggestion (PR #514) that would have been wrong to act on.

**4. Add to `CLAUDE.md`'s invariants — `@hyveon/shared` barrel hygiene.**

> `@hyveon/shared` is bundled into the Lambdas *and* imported by the renderer. New AWS-touching helpers go in a subpath module (`shared/src/aws/*.ts`) and are deep-imported — never added to `shared/src/index.ts`, whose barrel already pulls `@aws-sdk/client-dynamodb` and `@aws-sdk/client-secrets-manager` into anything that imports it. Prefer structural parameter types over SDK type imports.

Why: eight of the extractions proposed above cross into shared; without this rule the easy path (add to the barrel) silently grows the renderer bundle.

**5. Add to `.claude/rules/typescript-conventions.md` — `mountedRef` must re-arm under StrictMode.**

> The app renders under `<StrictMode>` (`web/src/main.tsx:18`), which mounts, unmounts, and remounts every component in dev. A `useRef(true)` "still mounted" guard **must** set `mountedRef.current = true` in the effect body, not only `false` in the cleanup — otherwise the simulated unmount permanently disables every post-await `setState` in that component. `guided-iam-step.component.tsx:180-186` is the correct pattern.

Why: incidental bug 2 below — two components have this exact defect today, and both TSDoc comments claim they "mirror" the correct one.

Both write `useRef(true)` plus a cleanup-only `useEffect(() => () => { mountedRef.current = false }, [])`. 3. **`CreateGamePayload`/`UpdateGamePayload` in the preload have drifted from shared** — `desktop-preload/src/hyveon-api.ts:539` declares `config: Omit<GameServer,'name'>` while `shared/src/gamesWrite.ts:119` declares `config: GameServerWriteConfig` (= `Omit<GameServer,'name'|'healthCheck'> & { healthCheck?: … }`). The preload's local `GameServer` (`:372-383`) **has no `healthCheck` field at all**, so `window.hyveon.games.create/update` is typed to reject the health-check payload the wizard actually builds (`networking-step.component.tsx:71`), and `api.service.ts:680-681` papers over it with `as Promise<GameWriteResult>`. Type-level only (structured clone does not care), but it silently disables type checking on the whole game-write path. Fixed by findings 30 and 31.

4. **a11y inconsistency: five error banners are not announced** — `ErrorBanner` (`web/src/pages/iac.page.tsx:353`) carries `role="alert"`; the five visually identical hand-rolled copies (`logs.page.tsx:207`, `infrastructure-logs.page.tsx:151`, `games.page.tsx:184`, `DiagnosticsPanel.tsx:168` and `:227`) do not. Screen readers announce IaC errors and stay silent for logs, games, and diagnostics errors. Finding 35 fixes it for free.

5. **Stale TSDoc cross-references to methods that do not exist** — `desktop-main/src/services/PulumiService.ts:5491` (and the same claim at `CloudHealthService.ts:262`, `GuidedIamService.ts:701`) says `readIsPackaged` "mirrors `ConfigService.readIsPackaged` exactly"; `ConfigService.ts` has no such method (verified by grep). `PulumiService.ts:5518` likewise cites a non-existent `ConfigService.readUserDataPath()`. Docs-only, but these comments are the stated justification for the duplication in findings 14–15, so they will mislead whoever does that cleanup.

6. **Asymmetric error-caching in `DiscordConfigService`** — `desktop-main/src/services/DiscordConfigService.ts:130-132` caches the `emptyConfig()` fallback into `this.cache` on failure, so a single transient DynamoDB error is memoized until `invalidateCache()`; `loadBase()` at `:157-158` returns its fallback *without* caching and retries on the next call. Undocumented and almost certainly unintentional in one direction. Resolve before finding 27 collapses the two onto one `SingleFlight`.

7. **Five controllers have no `@MessagePattern` channel-name guard at all** — verified: `cloud-health.controller.test.ts`, `diagnostics.controller.test.ts`, `files.controller.test.ts`, `iac-runs.controller.test.ts`, and `window.controller.test.ts` contain no `Reflect.getMetadata` reference, leaving **26 channels** unguarded (4 + 6 + 4 + 7 + 5). `env.controller.test.ts:21-24` documents that assertion as "the only automated guard that prevents a typo in the controller from silently breaking IPC." Renaming any of those 26 channel strings would break IPC at runtime with a green `npm run app:test`. Nearly free to fix once finding 58's `expectChannels()` helper exists — fold it into PR 6.

8. **`streamLambdaLogs` has no preload-level test coverage** — no reference to `logs.lambda.stream` appears anywhere in `desktop-preload/src/preload.test.ts`, while its sibling `streamLogs` is covered at `:508`. Not a defect in itself, but it means finding 34's extraction would be done blind. Add the tests first; that is why PR 17 is split in two.

9. **Two tests assert nothing explicitly** — `web/src/pages/games.page.test.tsx:252` ("should open the wizard pre-filled when Resume is clicked") ends at `await screen.findByText('Step 3 of 6: Networking');` with no `expect()`, and `web/src/components/add-game-wizard/add-game-wizard.component.test.tsx:309` ("should open pre-populated with an initialDraft and initialStepIndex") ends at `await screen.findByText('Step 2 of 6: Resources');` with no `expect()`. Both do fail correctly (RTL `findBy*` rejects on timeout), so these are weak rather than broken — but they fail with a 1000 ms "unable to find element" instead of a diff, and **neither actually asserts the pre-filled values its name promises**.

10. **`pathCopied` is never reset** — `web/src/components/first-run-wizard/guided-iam-step.component.tsx:485-493`, so "Path copied." stays on screen for the life of the phase. `discord.page.tsx:467-472` clears its equivalent after 1500 ms. Cosmetic asymmetry, looks unintended.

11. **`hexToBytes` accepts invalid hex silently** — `lambda/interactions/src/handler.ts:73-74`. `parseInt('0g', 16)` returns `0`, not `NaN`, so the `Number.isNaN(byte)` guard never fires for a byte whose *second* nibble is non-hex; a malformed signature yields a wrong byte instead of the intended `invalid hex` throw. Impact is contained — the `catch` at `:91-93` and a failed Ed25519 verify both return `false`, so the request is still rejected with 401 — but the guard does not do what its own error string claims. Do **not** "fix" this by switching to `Buffer.from(hex, 'hex')`, which truncates silently and changes the failure mode inside `verifySignature`.

12. **Pending-interaction row leaks when IP resolution fails** — `lambda/update-dns/src/handler.ts:255-259`. On `RUNNING` with `resolvePublicIp` returning `null`, the handler returns `{status:'error', reason:'no_ip'}` before reaching `notifyDiscordIfPending`, so the `PENDING#{taskArn}` row is never PATCHed or deleted. DynamoDB TTL reaps it after 15 minutes (`shared/src/ddb/pendingStore.ts:6`) and `getPending` short-circuits expired rows, so it self-heals — but the user's deferred Discord message is left hanging with no reply.

13. **`confirmRollback` does not abort on a destroyed renderer** — `desktop-main/src/controllers/iac.controller.ts:1525-1533`. The drain loop checks `!sender.isDestroyed()` only to decide whether to `send`, then keeps pulling `stream.next()` to completion. `plan` / `apply` / `destroy` (`:891`, `:1061`, `:1243`) instead `ac.abort(); await stream.return(undefined); return;`. A rollback whose window closes mid-run keeps a full Pulumi operation streaming to nobody. Behavioural, so out of scope for a cleanup PR — worth its own issue.

## Method

I fanned out to four parallel Opus judgment sub-agents split by package group — (a) `desktop-main` controllers and services, (b) `web` plus `desktop-preload`, (c) the six Lambda packages plus `shared` plus `cloud-aws`, (d) test code repo-wide — each briefed with the PR #538 / #537 / #514 reviewer comments as the calibration standard and required to cite verifiable `file:line`. I audited `infra` myself and, while the agents ran, independently derived a large part of the `web`, preload, and test sections by hand (the 18 duplicated bridge strings, the four preload generators, the seven-file PulumiService fixture duplication, the 59 logger mocks, the 189 error-normalization sites, md5-verified build-config duplication) so no area depended on a single agent completing. Before any grepping I mined the last 40 merged PRs' review comments for "duplicate / DRY / reuse / extract / helper / shared", which produced the calibration set (#538, #537, #514, #536, #511) and confirmed the owner's own threshold.

Every `file:line` in this report was re-read and confirmed by me directly rather than taken on an agent's word. Several agent-reported line numbers were off by a few lines and are corrected here (e.g. the `logs.controller.ts` stream handlers are at 152 and 283, not 147 and 264; `PulumiService` has 20 error classes, not 25; `api.service.ts` carries 24 mirror comments, not 34). One agent finding — "component specs bypass `renderPage()`", inherited from CodeRabbit on PR #514 — was **investigated and dropped as a false positive**, and rule 3 above now codifies why, so it does not get re-raised.

What I did **not** cover: dead code and unused exports (areas 01/02), documentation drift, dependency hygiene, and performance. I deliberately did not run `npx jscpd` (no package installs permitted) and relied on targeted greps, `md5sum` comparison, and `diff` of candidate blocks instead — which is why the build-config and log-group findings are stated as byte-identical rather than "similar."
