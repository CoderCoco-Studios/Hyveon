# App Diagnostics and Audit Trail Specs

EARS requirements for prefix `APP-DIAG`; design in `docs/intent/operator-app/diagnostics/diagnostics-design.md`.

## App Log File

- [x] **APP-DIAG-LOG-001**: Until `createLogger(logDir)` runs, the desktop-main `logger` binding shall be a console-only winston instance so modules imported before `main.ts` can log immediately. (observed: `logger.ts:48-54,61`)
- [x] **APP-DIAG-LOG-002**: When `createLogger(logDir)` is called, the desktop-main logger shall gain a `DailyRotateFile` transport writing `main-<YYYY-MM-DD>.log` in `logDir` and shall reassign the exported `logger` binding so every existing importer writes to the file. (observed: `logger.ts:72-90`)
- [x] **APP-DIAG-LOG-003**: The desktop-main log file transport shall retain daily `main-*.log` files for 14 days. (observed: `logger.ts:82`)
- [x] **APP-DIAG-LOG-004**: The desktop-main logger shall log at `info` level when `NODE_ENV` is `production` and at `debug` level otherwise, for both the console and file transports. (observed: `logger.ts:4,50,74`)
- [x] **APP-DIAG-LOG-005**: Where `NODE_ENV` is `production`, the desktop-main log file shall be written as one `timestamp()` + `json()` line per entry. (observed: `logger.ts:42`)
- [x] **APP-DIAG-LOG-006**: Where `NODE_ENV` is not `production`, the desktop-main log file shall be written as `HH:mm:ss [level] message` with any meta pretty-printed on continuation lines that repeat the prefix followed by a tab. (observed: `logger.ts:12-18,41`)
- [x] **APP-DIAG-LOG-007**: When running inside Electron, the desktop app shall write its log file to `<userData>/logs`; outside Electron, `DiagnosticsService` shall read from the `DIAGNOSTICS_LOG_DIR` environment value or `os.tmpdir()`. (observed: `main.ts:26`, `app.module.ts:105-110`)
- [ ] **APP-DIAG-LOG-008**: The desktop app shall derive the log directory used for writing (`createLogger`) and for reading (`DIAGNOSTICS_LOG_DIR` provider) from one shared helper so the two paths cannot drift. (observed; gap: `main.ts:26` and `app.module.ts:109` compute it independently)

## Log Tail Reads

- [x] **APP-DIAG-TAIL-001**: When `DiagnosticsService.readTail(maxLines)` is called, the service shall read at most the last 200 KB of today's `main-<YYYY-MM-DD>.log` (date in local time) and return at most `maxLines` entries. (observed: `DiagnosticsService.ts:9,86-93,109-138`)
- [x] **APP-DIAG-TAIL-002**: When `DiagnosticsService.readTail` reads a byte window that starts mid-line, the service shall drop the partial first fragment and any leading orphaned meta continuation lines rather than return a partial entry. (observed: `DiagnosticsService.ts:117-137`)
- [x] **APP-DIAG-TAIL-003**: When `DiagnosticsService.readTail` encounters dev-format meta continuation lines, the service shall merge them onto the preceding entry so `maxLines` counts `logger.*` calls, not physical lines. (observed: `DiagnosticsService.ts:48,59-69,138`)
- [x] **APP-DIAG-TAIL-004**: If today's log file does not exist when `DiagnosticsService.readTail` runs, then the service shall return an empty list without logging an error. (observed: `DiagnosticsService.ts:140-142`)
- [x] **APP-DIAG-TAIL-005**: If reading today's log file fails for any reason other than a missing file, then `DiagnosticsService.readTail` shall log a `warn` with the normalized message and throw a plain `Error` carrying only that message. (observed: `DiagnosticsService.ts:143-145`)
- [x] **APP-DIAG-TAIL-006**: When the renderer invokes `diagnostics.tail`, `DiagnosticsController` shall return `{ lines }` holding up to 500 tail entries; when it invokes `diagnostics.path`, it shall return `{ path }` naming today's log file. (observed: `diagnostics.controller.ts:47-59`)

## Renderer Error Reporting

- [x] **APP-DIAG-RERR-001**: When the renderer invokes `diagnostics.reportError` with `{ message, stack?, source }`, the desktop app shall write `renderer error (<source>): <message>` at `error` level with the stack as meta, and the handler shall not reject. (observed: `diagnostics.controller.ts:61-66`, `DiagnosticsService.ts:160-162`)
- [x] **APP-DIAG-RERR-002**: When a window `error` event or an `unhandledrejection` event fires in the renderer after `installGlobalErrorReporting()` has run, the renderer shall forward it via `reportRendererError` with source `window-error` or `unhandled-rejection` respectively. (observed: `report-renderer-error.utils.ts:165-174`)
- [x] **APP-DIAG-RERR-003**: When a React render crash reaches the top-level `ErrorBoundary`, the renderer shall forward the error message plus the combined error and component stack via `reportRendererError` with source `boundary`, and render a "Something went wrong" fallback in place of the app. (observed: `error-boundary.component.tsx:32-66`)
- [x] **APP-DIAG-RERR-004**: While the `ErrorBoundary` has caught a render crash, the renderer shall suppress React's default `onCaughtError` console echo so the crash is not logged a second time through console forwarding. (observed: `web/src/main.tsx:10-16`)
- [x] **APP-DIAG-RERR-005**: If no `window.hyveon.diagnostics.reportError` bridge exists, or the `reportError` IPC call rejects, then `reportRendererError` shall return silently without throwing. (observed: `report-renderer-error.utils.ts:150-159`)
- [ ] **APP-DIAG-RERR-006**: If a descendant of the top-level `ErrorBoundary` throws a falsy value (`0`, `''`, `null`), then the boundary shall still render its fallback rather than re-render the crashing children. (observed; gap: `error-boundary.component.tsx:55` tests `this.state.error` for truthiness)
- [ ] **APP-DIAG-RERR-007**: The `ErrorBoundary` fallback shall direct the operator to "Settings → Diagnostics", the section that actually hosts the log viewer. (observed; gap: `error-boundary.component.tsx:61` says "Settings → Logs", `settings.page.tsx:381`)
- [ ] **APP-DIAG-RERR-008**: When `installGlobalErrorReporting()` is called more than once in a renderer session, the renderer shall register its `error` and `unhandledrejection` listeners only once. (observed; gap: `report-renderer-error.utils.ts:165-174` has no install guard, unlike `:191`)
- [ ] **APP-DIAG-RERR-009**: When an `unhandledrejection` reason is an Error from another JS realm, the renderer shall report its message and stack, using the same cross-realm `isErrorLike` check as console formatting. (observed; gap: `report-renderer-error.utils.ts:171-172` uses `instanceof Error`)

## Renderer Console Forwarding

- [x] **APP-DIAG-CONS-001**: When renderer code calls `console.log`, `console.info`, `console.warn`, or `console.error` after `installConsoleForwarding()` has run, the renderer shall queue a `{ level, message }` entry for the `diagnostics.reportLog` IPC channel. (OpenSpec: app-diagnostics-logging / Renderer console forwarding to the main-process log; `report-renderer-error.utils.ts:190-206`)
- [x] **APP-DIAG-CONS-002**: While console forwarding is installed, the renderer shall call the original `console.*` method first so DevTools output is unchanged, and a forwarding failure shall never break the wrapped call. (OpenSpec: app-diagnostics-logging / Renderer console forwarding to the main-process log; `report-renderer-error.utils.ts:196-206`)
- [x] **APP-DIAG-CONS-003**: When the desktop app receives a `diagnostics.reportLog` batch, it shall write each entry as `renderer console (<level>): <message>` at the mapped winston level `log → debug`, `info → info`, `warn → warn`, `error → error`. (OpenSpec: app-diagnostics-logging / Renderer console forwarding to the main-process log; `DiagnosticsService.ts:26-34,177-180`)
- [x] **APP-DIAG-CONS-004**: If a `diagnostics.reportLog` entry carries an unrecognized level (including prototype keys such as `__proto__`), then the desktop app shall write it at `debug` level. (observed: `DiagnosticsService.ts:18-34,178`)
- [x] **APP-DIAG-CONS-005**: While console forwarding is installed, the renderer shall flush queued console entries to `diagnostics.reportLog` every 2,000 ms. (OpenSpec: app-diagnostics-logging / Renderer console forwarding to the main-process log; `report-renderer-error.utils.ts:14,208`)
- [x] **APP-DIAG-CONS-006**: When a console-forwarding flush runs with more than 50 queued entries, the renderer shall send the oldest 50 and keep the remainder queued for later flushes without dropping them. (OpenSpec: app-diagnostics-logging / Renderer console forwarding to the main-process log, scenario "A burst within the queue cap is delivered in full, not dropped"; `report-renderer-error.utils.ts:17,108-109`)
- [ ] **APP-DIAG-CONS-007**: When renderer console output arrives while the console-forwarding pending queue holds fewer than 200 entries, the renderer shall queue it rather than drop it. (OpenSpec: app-diagnostics-logging / Renderer console forwarding to the main-process log; gap: `report-renderer-error.utils.ts:68` drops at `queue.length + inFlightCount >= 200`, so up to 50 entries of headroom are reserved while a batch is in flight)
- [x] **APP-DIAG-CONS-008**: When renderer console entries have been dropped for queue capacity since the last flush, the next `diagnostics.reportLog` call shall carry the dropped count and the desktop app shall write a single `renderer console: N entries dropped (queue capacity exceeded)` warn line for that batch. (OpenSpec: app-diagnostics-logging / Renderer console forwarding to the main-process log, scenario "Entries beyond the queue cap are dropped and reported"; `report-renderer-error.utils.ts:67-73,110-117`, `DiagnosticsService.ts:182-185`)
- [x] **APP-DIAG-CONS-009**: If a single `diagnostics.reportLog` batch carries more than 200 entries, then the desktop app shall write only the first 200 and fold the overflow into the dropped-count warn line. (observed: `DiagnosticsService.ts:16,174-185`)
- [x] **APP-DIAG-CONS-010**: If a console-forwarding `diagnostics.reportLog` call throws synchronously or rejects, then the renderer shall requeue that batch at the front of the queue in its original order and restore its dropped count. (observed: `report-renderer-error.utils.ts:82-85,115-136`)
- [x] **APP-DIAG-CONS-011**: While a console-forwarding `diagnostics.reportLog` call is unsettled, the renderer shall not start another flush, preserving oldest-first delivery. (observed: `report-renderer-error.utils.ts:42,98-100`)
- [ ] **APP-DIAG-CONS-012**: If a console-forwarding `diagnostics.reportLog` call never settles, then the renderer shall recover (requeue the batch and resume flushing) rather than stop forwarding for the rest of the session. (observed; gap: `report-renderer-error.utils.ts:98-100,127-137` clears `flushInFlight` only on settle, contradicting its own doc at `:94-95`)
- [x] **APP-DIAG-CONS-013**: Where no `window.hyveon.diagnostics.reportLog` bridge exists (for example the Playwright `chromium` project), `installConsoleForwarding()` shall leave `console.*` untouched and not throw. (OpenSpec: app-diagnostics-logging / Renderer console forwarding to the main-process log, scenario "No bridge available"; `report-renderer-error.utils.ts:191`)
- [x] **APP-DIAG-CONS-014**: When `installConsoleForwarding()` is called more than once in a renderer session, the renderer shall wrap `console.*` and start the flush interval only once. (observed: `report-renderer-error.utils.ts:177,191-194`)
- [x] **APP-DIAG-CONS-015**: The renderer console-forwarding path shall apply no sanitization or redaction to console argument values; callers remain responsible for not logging secrets. (OpenSpec: app-diagnostics-logging / Renderer console forwarding to the main-process log; `report-renderer-error.utils.ts:45-58` formats arguments verbatim)

## Service-Layer Logging

- [x] **APP-DIAG-SVC-001**: When a method in `app/packages/desktop-main/src/services/*.ts` that calls an AWS SDK operation or the Pulumi engine is invoked, the method shall write a `logger.debug` entry naming the method and never its payload or arguments. (OpenSpec: app-diagnostics-logging / Service-layer diagnostic logging coverage, scenario "A service method's external call succeeds"; e.g. `DiagnosticsService.ts:111`, `AuditService.ts:89,133`, `DiagnosticsBundleService.ts:106`)
- [ ] **APP-DIAG-SVC-002**: If an AWS SDK or Pulumi call inside a `desktop-main/src/services/*.ts` method fails, then the method shall log the normalized message via `logger.warn` or `logger.error` before returning a modeled result or throwing a plain `Error`, and no raw SDK or Node error object shall propagate out of the method. (OpenSpec: app-diagnostics-logging / Service-layer diagnostic logging coverage, scenario "A service method's external call fails"; gap: `AuditService.ts:140` returns `store.listEntries(...)` with no catch)
- [ ] **APP-DIAG-SVC-003**: When `AuditService.record` logs a failed audit write, it shall log only the normalized error message, not the raw error object. (observed, `.claude/rules/logging.md` rule 2; gap: `AuditService.ts:114-118` logs `{ err }`)
- [x] **APP-DIAG-SVC-004**: The service-layer logging rule shall exempt pure helpers with no external call and no failure mode (for example `sleep.ts`, `mergeGameLists.ts`, `CostService.ts` arithmetic). (OpenSpec: app-diagnostics-logging / Service-layer diagnostic logging coverage)
- [x] **APP-DIAG-SVC-005**: When any `diagnostics.*` or `audit.list` IPC handler is invoked, the controller shall write a `logger.debug('<ControllerName>: <pattern> invoked')` line as its first statement, with no payload contents. (observed, `.claude/rules/logging.md` rule 1; `diagnostics.controller.ts:49,57,64,71,84,111`, `audit.controller.ts:26`)

## Log Secret Scrubbing

(OpenSpec: app-diagnostics-logging / Diagnostics bundle export, scenario "Log content is scrubbed before inclusion"; `diagnosticsLogScrubber.ts:5,33`)

(OpenSpec: app-diagnostics-logging / Diagnostics bundle export; `diagnosticsLogScrubber.ts:15-16,34-37`)
- [ ] **APP-DIAG-SCRUB-003**: When `scrubSecrets` processes a JSON-quoted labeled value as emitted by the production `json()` format (`"botToken":"..."`) or the dev meta format (`"apiKey": "..."`), it shall redact the value.
