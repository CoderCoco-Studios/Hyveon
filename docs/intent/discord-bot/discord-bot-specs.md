# Discord Bot Specs

EARS requirements for prefix `DISCORD`, the Discord Bot leaf described in `docs/intent/discord-bot/discord-bot-design.md`. No OpenSpec capability covers this leaf; requirements come from code, `docs/docs/app/discord.md`, the root `CLAUDE.md` invariants, and the Discord fragments of the `cost-visibility`, `game-port-visibility` and `pulumi-infra-program` capabilities.

## Serverless invariants

- [x] **DISCORD-SVC-001**: The Discord bot shall run without discord.js, without a gateway connection and without any long-running bot process, receiving every interaction as an HTTPS POST to a Lambda Function URL and calling Discord only over REST with global `fetch` (`patchOriginal.ts:23`, `DiscordCommandRegistrar.ts:90`). (observed; CLAUDE.md "Discord is fully serverless")
- [x] **DISCORD-SVC-002**: The Discord permission evaluator `canRun()` shall exist exactly once, in `@hyveon/shared`, and both the interactions Lambda and the followup Lambda shall import that single copy (`interactions/src/handler.ts:20-21`, `followup/src/handler.ts:24-26`). (observed; CLAUDE.md "`canRun()` lives in `@hyveon/shared`")
- [x] **DISCORD-SVC-003**: The interactions and followup Lambdas shall read their AWS region from the `AWS_REGION_` (trailing underscore) environment variable before falling back to the runtime's `AWS_REGION` (`interactions/src/handler.ts:56-58`, `followup/src/handler.ts:53-60`). (observed; CLAUDE.md "Lambda env vars use `AWS_REGION_`")
- [x] **DISCORD-SVC-004**: The Discord DynamoDB helpers in `@hyveon/shared` (`ddb/configStore.ts`, `ddb/pendingStore.ts`) shall use only the `@aws-sdk/lib-dynamodb` client the shared barrel already carries, adding no new AWS SDK package to the barrel. (observed; CLAUDE.md barrel invariant)
- [ ] **DISCORD-SVC-005**: The deployed stack shall expose the Discord interactions endpoint URL through exactly one stack output, read by exactly one desktop-side accessor. (observed; arrow Should Fix 6) (gap: `stackOutputs.ts:147` and `:156` carry identical `interactionsInvokeUrl`/`discordInteractionsUrl`; two unused `DiscordEventReceiver` implementations at `shared/src/discord/awsLambdaDiscordReceiver.ts:32` and `cloud-aws/src/AwsDiscordEventReceiver.ts:44-45`)

## Ingress and signature verification

- [x] **DISCORD-AUTH-001**: If a request to the interactions Lambda lacks either the `x-signature-ed25519` or the `x-signature-timestamp` header, then the interactions Lambda shall respond 401 without reading configuration (`interactions/src/handler.ts:269-271`). (observed)
- [x] **DISCORD-AUTH-002**: When verifying a Discord interaction signature, the interactions Lambda shall verify the Ed25519 signature over the timestamp concatenated with the raw request body as received (base64-decoded when flagged), never over a re-serialised body (`interactions/src/handler.ts:79-93`, `:132-136`). (observed)
- [x] **DISCORD-AUTH-003**: If the Discord public-key secret is missing or still holds the infra placeholder value, then the interactions Lambda shall respond 401 to every interaction (`interactions/src/handler.ts:275-277`, `secretsStore.ts:71-76`). (observed; OpenSpec: pulumi-infra-program / No secret material enters the stack, consumer side)
- [x] **DISCORD-AUTH-004**: If the Ed25519 signature on a Discord interaction fails to parse or verify, then the interactions Lambda shall respond 401 (`interactions/src/handler.ts:279-280`, `:90-92`). (observed)
- [x] **DISCORD-AUTH-005**: If a signature-verified Discord interaction body is not valid JSON, then the interactions Lambda shall respond 400 (`interactions/src/handler.ts:282-287`). (observed)
- [x] **DISCORD-AUTH-006**: When a signature-verified Discord interaction is a PING, the interactions Lambda shall respond with PONG without reading the Discord config table (`interactions/src/handler.ts:289-291`). (observed)
- [ ] **DISCORD-AUTH-007**: If the `x-signature-timestamp` of a Discord interaction is outside a bounded freshness window, then the interactions Lambda shall reject the request as a possible replay. (observed; arrow Should Fix 5) (gap: not implemented, `interactions/src/handler.ts:269-280` checks only the signature)
- [x] **DISCORD-AUTH-008**: The Discord public key read by the interactions Lambda shall be cached per warm container for at most 5 minutes (`secretsStore.ts:43-54`). (observed)

## Command handling (interactions Lambda)

- [x] **DISCORD-CMD-001**: For every signature-verified, non-PING Discord interaction, the interactions Lambda shall read the effective Discord config fresh from DynamoDB with no in-process cache (`interactions/src/handler.ts:293-294`). (observed)
- [x] **DISCORD-CMD-002**: When the interactions Lambda receives a slash command, it shall map `server-start` to the `start` action, `server-stop` to `stop`, and both `server-status` and `server-list` to `status` (`interactions/src/handler.ts:138-150`). (observed)
- [x] **DISCORD-CMD-003**: If a slash-command name is not one of the four Hyveon commands, then the interactions Lambda shall reply with an ephemeral "Unknown command" message and invoke nothing (`interactions/src/handler.ts:186`). (observed)
- [x] **DISCORD-CMD-004**: If a slash command arrives from a guild not in the effective `allowedGuilds`, then the interactions Lambda shall reply with an ephemeral "This bot is not enabled in this server." and invoke nothing (`interactions/src/handler.ts:188-191`). (observed; `docs/docs/app/discord.md` Guilds)
- [x] **DISCORD-CMD-005**: When an allowlisted guild issues `/server-list`, or `/server-status` with no game option, the interactions Lambda shall defer and hand the followup Lambda a `list` job, gated by the allowlist only (`interactions/src/handler.ts:197-219`). (observed)
- [x] **DISCORD-CMD-006**: If a game-bearing slash command (`/server-start`, `/server-stop`, or `/server-status` with a game) arrives without a game option where one is required, then the interactions Lambda shall reply with an ephemeral "Game is required." (`interactions/src/handler.ts:221`). (observed)
- [x] **DISCORD-CMD-007**: If `canRun` denies a game-bearing slash command, then the interactions Lambda shall reply with an ephemeral permission-denied message naming the action and game, and invoke nothing (`interactions/src/handler.ts:223-225`). (observed)
- [x] **DISCORD-CMD-008**: When a game-bearing slash command passes `canRun`, the interactions Lambda shall async-invoke the followup Lambda (`InvocationType: 'Event'`) with the action, application ID, interaction token, user, guild, roles and game, and reply with an ephemeral deferred response (type 5) (`interactions/src/handler.ts:119-125`, `:227-236`, `:249-258`). (observed)
- [ ] **DISCORD-CMD-009**: The interactions Lambda shall return its deferred slash-command acknowledgement within Discord's 3-second reply budget regardless of followup-invoke API latency, as its module header states. (observed; `interactions/src/handler.ts:13-15`) (gap: `interactions/src/handler.ts:198-236` awaits `InvokeCommand` before returning the ack)
- [x] **DISCORD-CMD-010**: When the interactions Lambda receives an autocomplete interaction for the `game` option, it shall answer in-band with up to 25 games from the deploy-time `GAME_NAMES` list that contain the typed text (case-insensitive) and that `canRun` allows for the command's action (`interactions/src/handler.ts:152-178`). (observed; `docs/docs/app/discord.md:336-338`)
- [x] **DISCORD-CMD-011**: If an autocomplete interaction has no focused `game` option or names an unknown command, then the interactions Lambda shall answer with an empty choice list (`interactions/src/handler.ts:159-164`). (observed)
- [x] **DISCORD-CMD-012**: If a signature-verified Discord interaction is neither PING, autocomplete, nor application command, then the interactions Lambda shall reply with an ephemeral "Unsupported interaction type." (`interactions/src/handler.ts:303`). (observed)
- [x] **DISCORD-CMD-013**: The four Discord slash commands shall be `server-start` and `server-stop` (required, autocompleted `game` string option), `server-status` (optional, autocompleted `game` option) and `server-list` (no options) (`shared/src/commands.ts:29-73`). (observed)

## Permission evaluation (canRun)

- [x] **DISCORD-PERM-001**: If the interaction's guild is not in the effective `allowedGuilds`, then `canRun` shall deny regardless of admin status or per-game entries (`canRun.ts:29`). (observed; `docs/docs/app/discord.md:340-341`)
- [x] **DISCORD-PERM-002**: While the guild is allowlisted, `canRun` shall allow any action on any game, including games with no permission entry, for a user in `admins.userIds` or a member holding any role in `admins.roleIds` (`canRun.ts:30-31`). (observed)
- [x] **DISCORD-PERM-003**: While the guild is allowlisted and the caller is not an admin, `canRun` shall deny when the game has no `gamePermissions` entry or the entry's `actions` omits the requested action (`canRun.ts:32-34`). (observed)
- [x] **DISCORD-PERM-004**: While the guild is allowlisted, the caller is not an admin, and the game's entry includes the requested action, `canRun` shall allow if the user is in the entry's `userIds` or holds any role in its `roleIds`, and deny otherwise (`canRun.ts:35-37`). (observed)
- [x] **DISCORD-PERM-005**: `canRun` shall be a pure function of the effective Discord config and the caller's guild, user, roles, game and action, performing no I/O (`canRun.ts:19-38`). (observed)

## Followup Lambda

- [x] **DISCORD-RUN-001**: When the followup Lambda handles a `start`, `stop` or game-bearing `status` job, it shall re-read the effective Discord config and re-check `canRun` before doing any ECS work, replying with a permission-denied message if the check now fails (`followup/src/handler.ts:219-228`, `:247-263`). (observed)
- [x] **DISCORD-RUN-002**: When the followup Lambda handles a permitted `start` job and no task for that game is running, it shall issue one Fargate `RunTask` against the `{game}-server` task definition with a public IP and `propagateTags: 'TASK_DEFINITION'` (`followup/src/handler.ts:126-138`). (observed)
- [x] **DISCORD-RUN-003**: When the followup Lambda starts a game server via `RunTask` for a Discord `/server-start`, the resulting ECS task shall carry a `Game` tag equal to the game's id, inherited from its task definition through `propagateTags` (`followup/src/handler.ts:136`). (OpenSpec: cost-visibility / Launching a game server from the Discord `/start` command)
- [x] **DISCORD-RUN-004**: If a task for the requested game is already running when the followup Lambda handles `start`, then it shall reply that the game is already running and issue no `RunTask` (`followup/src/handler.ts:123-124`). (observed)
- [x] **DISCORD-RUN-005**: If `RunTask` returns no task ARN, then the followup Lambda shall reply with the first ECS failure reason, or "unknown" (`followup/src/handler.ts:139-143`). (observed)
- [x] **DISCORD-RUN-006**: When the followup Lambda handles a permitted `stop` job, it shall `StopTask` the game's running task with reason "Stopped via Discord", or reply that the game is not running if none is found (`followup/src/handler.ts:150-162`). (observed)
- [x] **DISCORD-RUN-007**: When the followup Lambda handles a `list` job, it shall report status only for `GAME_NAMES` games the caller may `status` under `canRun`, one line per game, and reply that the caller may view none when the filtered list is empty (`followup/src/handler.ts:164-179`). (observed)
- [x] **DISCORD-RUN-008**: When the followup Lambda reports a game's status, it shall derive `running`, `starting` or `stopped` from the `{game}-server` family's RUNNING-desired tasks and, for a RUNNING task, resolve its public IP from the task's ENI (`followup/src/handler.ts:79-116`). (observed)
- [x] **DISCORD-RUN-009**: When the followup Lambda finishes any job, it shall PATCH the deferred interaction's `@original` message with the result, authenticating with the interaction token rather than the bot token (`followup/src/handler.ts:272`, `patchOriginal.ts:22-23`). (observed)
- [ ] **DISCORD-RUN-010**: If any step of the followup Lambda fails, including the effective-config read and the final PATCH, then the followup Lambda shall still resolve the deferred Discord interaction with an error reply. (observed; arrow Must Fix 2) (gap: `followup/src/handler.ts:240` and `:272` sit outside the `try`)
- [ ] **DISCORD-RUN-011**: The followup Lambda shall never write the Discord interaction token to its logs. (observed; `.claude/rules/logging.md` rule 3 intent; arrow Must Fix 3) (gap: `followup/src/handler.ts:268` logs the whole event)
- [ ] **DISCORD-RUN-012**: If an ECS call fails inside the followup Lambda, then the Discord reply shall carry a generic failure message and the raw exception text shall go only to the server-side log. (observed; arrow Should Fix 4) (gap: `String(err)` in replies at `followup/src/handler.ts:114`, `:146`, `:160`)
- [x] **DISCORD-RUN-013**: If an unexpected error is thrown while the followup Lambda handles a job, then it shall reply "Command failed. Check server logs." (`followup/src/handler.ts:267-270`). (observed)
- [ ] **DISCORD-RUN-014**: If the Discord webhook PATCH request itself rejects (network failure), then `patchInteractionOriginal` shall log and swallow the failure, as its TSDoc states. (observed; `patchOriginal.ts:9-11`) (gap: `patchOriginal.ts:23` does not wrap `fetch`)
- [x] **DISCORD-RUN-015**: If Discord answers the webhook PATCH with a non-2xx status, then `patchInteractionOriginal` shall log the status and response body without throwing (`patchOriginal.ts:28-31`). (observed)

## Pending interactions

- [x] **DISCORD-PEND-001**: When the followup Lambda's `RunTask` for a Discord `/server-start` returns a task ARN, it shall write a `PENDING#{taskArn}` row holding the application ID, interaction token, user, guild, game and action (`followup/src/handler.ts:190-200`, `pendingStore.ts:13-30`). (observed)
- [x] **DISCORD-PEND-002**: Every `PENDING#{taskArn}` row shall carry an `expiresAt` DynamoDB TTL 15 minutes after it is written, matching the Discord interaction-token lifetime (`pendingStore.ts:5-6`, `:17`). (observed)
- [x] **DISCORD-PEND-003**: If a `PENDING#{taskArn}` row is read after its `expiresAt`, then `getPending` shall treat it as absent and best-effort delete it, because the TTL sweeper can lag (`pendingStore.ts:42-61`). (observed)
- [x] **DISCORD-PEND-004**: `getPending` shall read `PENDING#{taskArn}` rows with consistent reads (`pendingStore.ts:43-48`). (observed)

## Message rendering

- [x] **DISCORD-MSG-001**: When rendering a game's status for Discord, `formatGameStatus` shall emit one status line with a state emoji, the bold game name and the state, followed for a running game with a connect-message template by the rendered template on a second line (`formatStatus.ts:43-55`). (observed)
- [x] **DISCORD-MSG-002**: When rendering a connect-message template, `renderConnectMessage` shall substitute `{host}`, `{ip}`, `{port}` and `{game}`, rendering absent values as empty (`formatStatus.ts:16-31`). (observed)
- [x] **DISCORD-MSG-003**: When the followup Lambda replies to a successful `/server-start` for a game with a connect-message template, it shall append the template rendered with the `{game}.{domain}` host and a blank `{ip}`, since no public IP exists yet (`followup/src/handler.ts:201-209`). (observed)
- [x] **DISCORD-MSG-004**: When the Discord `GAME_PORTS` mapping is built for a non-HTTPS game, it shall use the first non-`icmp` port, preferring a public-visibility one, so that an `icmp` entry listed first is never presented as the connect port (`infra/src/lambdas.ts:307-322`). - [x] **DISCORD-MSG-005**: When a Discord connect message is rendered for an HTTPS game, it shall present the `https://{game}.{hosted_zone_name}` URL form (port 443) and never `webPort` or an additional port (`infra/src/lambdas.ts:310-313`, `formatStatus.ts:20-25`, `:57`). (OpenSpec: game-port-visibility / Connect-port surfaces exclude ICMP entries / HTTPS game connect message)
- [x] **DISCORD-MSG-006**: The followup Lambda and the update-dns Lambda shall render Discord status and connect messages through the same `@hyveon/shared` `formatStatus.ts` functions (`followup/src/handler.ts:178`, `:184`, `:207`). (observed)

## Configuration model

- [x] **DISCORD-CFG-001**: The operator-edited Discord configuration (`clientId`, `allowedGuilds`, `admins`, `gamePermissions`) shall live in the `CONFIG#discord` row of the Discord DynamoDB table (`configStore.ts:7-11`, `:149-165`). (observed)
- [x] **DISCORD-CFG-002**: The infra-seeded base Discord configuration (`allowedGuilds`, `admins` from `baseAllowedGuilds`/`baseAdminUserIds`/`baseAdminRoleIds`) shall live in the `BASE#discord` row, which the desktop app only reads (`configStore.ts:7-11`, `escapes.ts:13-15`). (observed; `docs/docs/app/discord.md` Base config guilds)
- [x] **DISCORD-CFG-003**: When either Lambda reads the effective Discord config, `getEffectiveDiscordConfig` shall return the set-union of base and dynamic `allowedGuilds`, admin user IDs and admin role IDs, and take `clientId` and `gamePermissions` from the dynamic row only (`configStore.ts:105-122`). - [x] **DISCORD-CFG-004**: When reading a Discord config row, the config store shall use consistent reads and drop non-string entries and prototype-unsafe game keys, so that a hand-edited item cannot crash a Lambda (`configStore.ts:28-67`, `sanitize.ts:11`, `:26`). (observed)

- [x] **DISCORD-CFG-006**: The Discord Lambdas shall read only the public-key secret; the bot token shall be used solely by the desktop command registrar (`interactions/src/handler.ts:275-276`, `DiscordCommandRegistrar.ts:80`). (observed)

## Dropped from OpenSpec

None. No OpenSpec capability is carried by this leaf, and every Discord fragment translated above from `cost-visibility`, `game-port-visibility` and `pulumi-infra-program` still describes current behaviour. The infra-side scenarios of `pulumi-infra-program / No secret material enters the stack` (placeholder creation, create-only secret versions, no-diff previews, the preservation test) stay with `iac/program`.
