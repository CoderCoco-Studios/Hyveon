# Game Server Specs

EARS requirements for the `GAME` prefix; design and rationale live in `docs/intent/game-server/game-server-design.md`.

## Game Server Model

- [x] **GAME-MODEL-001**: The system shall represent each declared game as one entry of the `gameServers` map in `deployment-config.json`, keyed by the game name, with the stored value carrying `image`, `cpu`, `memory`, `ports`, `volumes` and the optional `webPort`, `https`, `environment`, `command`, `file_seeds`, `connect_message`, `healthCheck` and `pinnedHostname` fields. (observed)
- [x] **GAME-MODEL-002**: Whenever a declared game crosses the IPC boundary to the renderer (`games.list`, `games.create`, `games.update`), the system shall replace its `healthCheck.auth` with a `secretSet` boolean and an `authType`, never the secret ARN or credential. (observed)
- [x] **GAME-MODEL-003**: The games list (`games.list` and the refreshed list returned by every successful game write) shall return one entry per game that is declared in `deployment-config.json` or present in the deployed stack's `gameNames` output, each flagged `declared` and `deployed`, carrying the redacted config when declared and any drift finding for that game. (observed)
- [x] **GAME-MODEL-004**: The games list shall order entries as declared games in `deployment-config.json` order, followed by deployed-only games in stack-output order. (observed)

## Shared Validation

- [x] **GAME-VALID-001**: The renderer (add-game wizard and edit-game form) and the main-process game write path shall both validate a proposed game entry with the single `validateGameServer` function exported from `@hyveon/shared`, so both report identical issue paths and messages. (observed)
- [x] **GAME-VALID-002**: When `validateGameServer` rejects a proposed game entry, it shall return every issue found, each positioned with a JSON-path-like `path` (for example `ports[1]`, `volumes[0].container_path`, `webPort`). (observed)
- [x] **GAME-VALID-003**: When a proposed game entry fails the structural parse on an unrelated field, `validateGameServer` shall still run the port-collision, HTTPS, `webPort`, ICMP and deployment-wide reserved-port rules on the raw `ports`, `https` and `webPort` values, so an incomplete wizard draft still receives networking feedback. (observed)
- [x] **GAME-VALID-004**: The game validator shall reject a `cpu`/`memory` pair that is not a valid AWS Fargate task size (cpu 256 with memory 512/1024/2048; each higher tier with its stepped memory range), with the issue at `cpu` or `memory`. (observed)
- [x] **GAME-VALID-005**: The game validator shall reject a game entry with no `volumes` entry, any volume with an empty `name` or `container_path`, any volume `container_path` that is not absolute, and any `file_seeds[].path` that is not absolute. (observed)
- [x] **GAME-VALID-006**: The game validator shall reject any `{token}` in a game's `connect_message` other than `{host}`, `{ip}`, `{port}` and `{game}`, with the issue at `connect_message`. (observed)
- [x] **GAME-VALID-007**: When a game is created, the system shall reject a name that does not match `GAME_NAME_PATTERN` (a lowercase DNS-safe label of 1-32 characters), in both the add-game wizard and `DeploymentConfigService` when it inserts the entry. (observed)
- [x] **GAME-VALID-008**: While editing an already-declared game, the system shall not re-validate its name against the create-time name pattern, and the edit-game form shall render the name read-only. (observed)
- [x] **GAME-VALID-009**: The add-game wizard shall reject an empty or whitespace-only `image`, which the shared schema alone accepts. (observed)
- [ ] **GAME-VALID-010**: The game validator shall reject any `ports[N].protocol` other than the exact lowercase strings `tcp`, `udp` and `icmp` for every game, HTTPS or not. (observed) (gap: `gameServerValidator.ts:77` accepts any string; the tcp/udp check exists only for HTTPS games at `:753`)
- [ ] **GAME-VALID-011**: Every protocol comparison in the game validator and the shared port helpers shall treat `protocol` case-insensitively, or the value shall be normalised to lowercase on read, so a hand-edited `TCP` behaves the same as `tcp` in every rule. (observed) (gap: `checkHttpsPortRules` compares exactly at `gameServerValidator.ts:753,765`, the health-check port rule at `:1001`, `normalizeGameServer` at `gameServerPorts.ts:62`; `portKey`, `isTcpPort` and `isCaddyReservedPort` lowercase)

## Resource Picker

- [x] **GAME-RES-001**: The add-game wizard's Resources step and the edit-game form's Resources section shall present vCPU and memory as two slider controls, not dropdowns, rendered by the same component. (OpenSpec: game-resource-picker / vCPU and memory selected via constrained sliders; Resource selection applies to both add and edit flows)
- [x] **GAME-RES-002**: The vCPU slider in the game Resources step shall stop only at the seven Fargate vCPU tiers (0.25, 0.5, 1, 2, 4, 8, 16 vCPU). (OpenSpec: game-resource-picker / vCPU and memory selected via constrained sliders)
- [x] **GAME-RES-003**: The memory slider in the game Resources step shall reach exactly the valid Fargate memory values for the selected vCPU tier, including the unevenly spaced 512/1024/2048 MiB values at 0.25 vCPU and the 4 GiB and 8 GiB steps at 8 and 16 vCPU. (OpenSpec: game-resource-picker / vCPU and memory selected via constrained sliders)
- [x] **GAME-RES-004**: When the operator changes the vCPU slider in the game Resources step so that the selected memory is no longer valid for the new tier, the system shall reset memory to unset rather than re-clamp it. (OpenSpec: game-resource-picker / vCPU and memory selected via constrained sliders)
- [x] **GAME-RES-005**: When the edit-game form opens, its Resources sliders shall be pre-populated with the game's declared `cpu` and `memory`. (OpenSpec: game-resource-picker / Resource selection applies to both add and edit flows)
- [x] **GAME-RES-006**: While both vCPU and memory are selected in the game Resources step, the system shall show a live hourly Fargate cost estimate computed by the same formula the Costs page uses. (observed)

## Environment Variables

- [x] **GAME-ENV-001**: The add-game wizard shall expose a game's `environment` rows in a dedicated Environment step between the Storage and Review steps, and the edit-game form shall expose them in an Environment section alongside Identity, Resources, Networking and Storage. (OpenSpec: game-environment-variables / Operators can set a game's environment variables from the game form)
- [x] **GAME-ENV-002**: The game environment editor shall let the operator add a blank row, edit any row's `name` or `value`, and remove any row, with no minimum row count. (OpenSpec: game-environment-variables / Operators can set a game's environment variables from the game form)
- [x] **GAME-ENV-003**: When the operator adds environment rows in the add-game wizard and submits, the create payload's config shall carry those rows as `environment`; when no row was added, the payload shall carry no `environment` entries. (OpenSpec: game-environment-variables / Operators can set a game's environment variables from the game form)
- [x] **GAME-ENV-004**: When the edit-game form opens for a game with declared environment variables, the Environment section shall render one pre-filled row per declared variable. (OpenSpec: game-environment-variables / Operators can set a game's environment variables from the game form)
- [x] **GAME-ENV-005**: When the operator saves the edit-game form, the update payload's `environment` shall reflect rows added or removed in the form and shall carry the declared rows unchanged when only an unrelated field was edited. (OpenSpec: game-environment-variables / Operators can set a game's environment variables from the game form)
- [x] **GAME-ENV-006**: The game validator shall reject any `environment[N]` row with an empty `name`, and any row whose `name` duplicates an earlier row's `name` in the same game, with the issue at `environment[N].name`, on every game write path. (OpenSpec: game-environment-variables / Environment variable entries must have a non-empty, unique name)
- [x] **GAME-ENV-007**: The game validator shall place no constraint on an environment row's `name` character set or casing beyond non-emptiness, except for rows whose value uses `${hyveon.network.public-ipv4}` (see GAME-TOKEN-009). (OpenSpec: game-environment-variables / Environment variable entries must have a non-empty, unique name)
- [x] **GAME-ENV-008**: When a game environment row has a name or value issue, the add-game wizard and edit-game form shall block submission and display the issue next to that row's name or value input. (OpenSpec: game-environment-variables / Environment variable entries must have a non-empty, unique name; The environment editor surfaces the available interpolation tokens)
- [x] **GAME-ENV-009**: The game environment editor (add-game wizard Environment step and edit-game form Environment section) shall show a hint listing `${hyveon.network.public-address}` and `${hyveon.network.public-ipv4}` with a short description of each. (OpenSpec: game-environment-variables / The environment editor surfaces the available interpolation tokens)
- [x] **GAME-ENV-010**: The game Environment step shall let the operator edit an optional `command` list of container start-command arguments, and the game validator shall reject an empty `command` argument. (observed)

## Env Token Interpolation

- [x] **GAME-TOKEN-001**: The system shall support the `${hyveon.<namespace>.<name>}` token grammar in game environment values against a fixed allow-list exported from `@hyveon/shared`, which is exactly `${hyveon.network.public-address}` and `${hyveon.network.public-ipv4}`. (OpenSpec: env-token-interpolation / Environment variable values support an allow-listed ${hyveon.*} token grammar)
- [x] **GAME-TOKEN-002**: The game validator shall accept an allow-listed token embedded anywhere in a longer environment value and shall accept several tokens in one value. (OpenSpec: env-token-interpolation / Environment variable values support an allow-listed ${hyveon.*} token grammar)
- [x] **GAME-TOKEN-003**: If a game environment value contains a `${hyveon.`-prefixed sequence (closed or unclosed) that is not on the allow-list, then the game validator shall reject it with an issue at that row's `environment[N].value` path naming the unknown token and listing the allowed tokens. (OpenSpec: env-token-interpolation / Environment variable values support an allow-listed ${hyveon.*} token grammar; game-environment-variables / Environment variable entries must have a non-empty, unique name)
- [x] **GAME-TOKEN-004**: The system shall treat all game environment value content other than `${hyveon.*}` sequences, including `${OTHER_VAR}` shell syntax and brace text, as opaque data that passes validation and reaches the container definition byte-for-byte. (OpenSpec: env-token-interpolation / Environment variable values support an allow-listed ${hyveon.*} token grammar; game-environment-variables / Environment variable entries must have a non-empty, unique name)
- [x] **GAME-TOKEN-005**: When the infra program builds a game's task definition, it shall replace every `${hyveon.network.public-address}` in that game's environment values with `<game>.<zone>`, baked into the task definition with no runtime component. (OpenSpec: env-token-interpolation / The public-address token resolves to the game's hostname at deploy time)
- [x] **GAME-TOKEN-006**: If no hosted zone is configured when the infra program runs, then the preview/apply shall fail before any task definition carrying an unresolved `${hyveon.network.public-address}` is created. (OpenSpec: env-token-interpolation / The public-address token resolves to the game's hostname at deploy time) Note: `defineAll` rejects any empty zone first with a generic message (`infra/src/program.ts:163-167`); the error naming the game and token (`infra/src/ecs.ts:129`) is defense in depth.
- [x] **GAME-TOKEN-007**: Where a game's environment values use `${hyveon.network.public-ipv4}`, the infra program shall leave the raw token in the task definition and set the game container's `entryPoint` to a generated `/bin/sh -c` wrapper that discovers the public IPv4 from `https://checkip.amazonaws.com` (wget, falling back to curl), re-exports exactly the token-bearing variables with the IP substituted, and then `exec`s the game's `command`. (OpenSpec: env-token-interpolation / The public-ipv4 token resolves at container boot via an injected entrypoint wrapper)
- [ ] **GAME-TOKEN-008**: The ipv4 entrypoint wrapper shall bound its public-IPv4 discovery retries by a total budget of approximately 60 seconds. (OpenSpec: env-token-interpolation / The public-ipv4 token resolves at container boot via an injected entrypoint wrapper) (gap: `infra/src/envTokenWrapper.ts:64-92` runs 30 attempts of `wget -T 5` then `curl -m 5` plus `sleep 2`, so the worst case is several minutes when each attempt times out rather than failing fast [inferred from the script])
- [x] **GAME-TOKEN-009**: If a game environment row's value uses `${hyveon.network.public-ipv4}` and its `name` is not a shell identifier (`[A-Za-z_][A-Za-z0-9_]*`), then the game validator shall reject it with an issue at `environment[N].name`. (OpenSpec: env-token-interpolation / Wrapper script generation is injection-safe)
- [x] **GAME-TOKEN-010**: Where a game's environment values do not use `${hyveon.network.public-ipv4}`, the infra program shall set no `entryPoint` on that game's container. (OpenSpec: env-token-interpolation / The public-ipv4 token resolves at container boot via an injected entrypoint wrapper)
- [x] **GAME-TOKEN-011**: If the ipv4 entrypoint wrapper cannot obtain a well-formed IPv4 address within its retry loop, then it shall exit non-zero without starting the game process, so the task stops and surfaces through stopped-task visibility. (OpenSpec: env-token-interpolation / Boot-time discovery failure fails the server start visibly)
- [x] **GAME-TOKEN-012**: The ipv4 wrapper generator shall embed every operator-supplied environment value and command argument only inside single-quoted shell strings with embedded quotes escaped as `'\''`, and shall splice the discovered IP through a shell variable, so operator content cannot inject shell syntax. (OpenSpec: env-token-interpolation / Wrapper script generation is injection-safe)
- [x] **GAME-TOKEN-013**: The game model shall support an optional `command` string array that the infra program passes through verbatim as the game container's `command`, whether or not any token is used. (OpenSpec: env-token-interpolation / Games gain an optional container start command, required with the ipv4 token)
- [x] **GAME-TOKEN-014**: If a game's environment values use `${hyveon.network.public-ipv4}` while `command` is absent or empty, then the game validator shall reject the entry with an issue at `command` explaining that the boot wrapper replaces the image's start command. (OpenSpec: env-token-interpolation / Games gain an optional container start command, required with the ipv4 token)

## HTTPS

- [x] **GAME-HTTPS-001**: The add-game wizard and the edit-game form shall expose a game's `https` flag as a toggle in the Networking step, defaulting to off for a new game and reflecting the declared value when editing. (OpenSpec: game-https-configuration / Operators can set a game's HTTPS flag from the game form)
- [x] **GAME-HTTPS-002**: When the operator submits the add-game wizard or the edit-game form, the payload shall always carry `https` as an explicit boolean: `true` when the toggle is on, `false` when it is off or was never touched, and the declared value unchanged when only another field was edited. (OpenSpec: game-https-configuration / Operators can set a game's HTTPS flag from the game form)
- [x] **GAME-HTTPS-003**: When a game is written through the game write path, its `https` value shall persist to `deployment-config.json` as written (an explicit `false` stays `false` rather than being omitted) and shall be read back into the edit-game form, with no other field disturbed. (OpenSpec: game-https-configuration / The HTTPS flag round-trips through the deployment-config JSON)
- [x] **GAME-HTTPS-004**: The game model shall carry an optional `webPort` naming the container port the Caddy sidecar proxies to, never implied by the order of `ports`. (OpenSpec: game-https-configuration / An HTTPS-enabled game declares an explicit web port)
- [x] **GAME-HTTPS-005**: While a game has `https: true`, the game validator shall require `webPort` to be present, an integer from 1 to 65535, and neither 80 nor 443, reporting each violation at `webPort` with a message explaining the rule. (OpenSpec: game-https-configuration / An HTTPS-enabled game declares an explicit web port)
- [x] **GAME-HTTPS-006**: If a game with `https` false or omitted declares `webPort`, then the game validator shall reject it with an issue at `webPort` stating it is only valid when HTTPS is enabled. (OpenSpec: game-https-configuration / An HTTPS-enabled game declares an explicit web port)
- [x] **GAME-HTTPS-007**: While a game has `https: true`, the game validator shall reject any `ports[N]` entry whose protocol is not `tcp` or `udp`, any entry on container port 80 or 443, and any `tcp` entry equal to `webPort`, each pathed at `ports[N]`, and shall accept an empty `ports` list or a first entry using `udp`. (OpenSpec: game-https-configuration / An HTTPS-enabled game must satisfy the Caddy sidecar's port constraints)
- [x] **GAME-HTTPS-008**: While a game has `https` false or omitted, the game validator shall apply none of the HTTPS port constraints to that game's own `ports`. (OpenSpec: game-https-configuration / An HTTPS-enabled game must satisfy the Caddy sidecar's port constraints)
- [x] **GAME-HTTPS-009**: The game validator shall reject a `tcp` `ports` entry on one game that equals another game's `webPort`, and a `webPort` that equals another game's `tcp` `ports` entry, in either edit order, with the issue at the offending `ports[N]` or `webPort` naming the other game. (OpenSpec: game-https-configuration / An HTTPS-enabled game must satisfy the Caddy sidecar's port constraints, constraint 5 from the `https-explicit-web-port` delta; not yet in the main spec)
- [x] **GAME-HTTPS-010**: When the Pulumi preview/apply reads `deployment-config.json` directly, the system shall re-check the cross-game `webPort` collision of GAME-HTTPS-009 and refuse the run with an error naming both games if one exists. (observed)
- [x] **GAME-HTTPS-011**: While the HTTPS toggle is on, the game Networking step shall render a dedicated web-port field, separate from the port list, labelled as the port the game's web server listens on and stating that Caddy serves it publicly on 443, and shall label the port list as optional additional ports. (OpenSpec: game-https-configuration / The form blocks a save the shared validator would reject)
- [x] **GAME-HTTPS-012**: While the HTTPS toggle is off, the game Networking step shall render no web-port field and the submitted payload shall carry no `webPort`. (OpenSpec: game-https-configuration / The form blocks a save the shared validator would reject)
- [x] **GAME-HTTPS-013**: While an HTTPS constraint violation remains, the add-game wizard and edit-game form shall disable advancing or saving, and shall attribute issues pathed at `webPort` or `ports[N]` to the Networking step, clearing them once the input is corrected. (OpenSpec: game-https-configuration / The form blocks a save the shared validator would reject)
- [x] **GAME-HTTPS-014**: While the HTTPS toggle is on, the game Networking step shall show an inline warning callout beside it stating that ports 443 and 80 open to the internet for the whole stack, that the web port is no longer directly reachable and is reached through the sidecar (additional ports following their own visibility), and that first boot performs a Let's Encrypt (ACME) issuance requiring the game's hostname to resolve to the running task; while the toggle is off, no callout shall render. (OpenSpec: game-https-configuration / Operators are warned about the consequences of enabling HTTPS)
- [x] **GAME-HTTPS-015**: When `DeploymentConfigService` reads a legacy game with `https: true` and no `webPort`, it shall return `webPort` equal to the first `ports` entry's `container` and `ports` equal to the remaining entries, idempotently, without operator action, persisting the new shape only on the next ordinary save; configs that already declare `webPort` shall pass through unchanged. (OpenSpec: game-https-configuration / Legacy HTTPS configs are normalised on read)
- [x] **GAME-HTTPS-016**: When the add-game wizard draft is read back from storage, the system shall apply the same legacy HTTPS normalisation as GAME-HTTPS-015. (OpenSpec: game-https-configuration / Legacy HTTPS configs are normalised on read)
- [x] **GAME-HTTPS-017**: If a legacy HTTPS game's first `ports` entry is not `tcp` or has no container yet, then the legacy normaliser shall leave the game unchanged so validation reports the missing `webPort` rather than guessing. (observed; refines GAME-HTTPS-015, which the OpenSpec states unconditionally)

## Ports, Visibility and ICMP

- [x] **GAME-PORT-001**: The game model shall accept an optional per-port `visibility` of exactly `'public'` or `'internal'`, and every consumer (security-group ingress, wizard display, validation) shall treat an omitted `visibility` as `'public'`, so configs written before the field existed behave unchanged. (OpenSpec: game-port-visibility / Per-port visibility field)
- [x] **GAME-PORT-002**: If a game port declares a `visibility` other than `'public'` or `'internal'`, then the game validator shall reject the configuration with an issue identifying the offending port. (OpenSpec: game-port-visibility / Per-port visibility field)
- [x] **GAME-PORT-003**: The infra program shall ingress every game port with effective visibility `'public'` on the `game_servers` security group from `0.0.0.0/0`, and every `'internal'` port from the VPC CIDR block only, with no `0.0.0.0/0` rule for it, for HTTPS games' additional ports exactly as for non-HTTPS games. (OpenSpec: game-port-visibility / Internal ports are ingressed from the VPC CIDR block only; Port visibility applies to an HTTPS game's additional ports)
- [x] **GAME-PORT-004**: The infra program shall give an HTTPS game's `webPort` no security-group ingress of its own, so it is reachable only through the Caddy sidecar's public 443/80 ingress. (OpenSpec: game-port-visibility / Internal ports are ingressed from the VPC CIDR block only; Port visibility applies to an HTTPS game's additional ports)
- [x] **GAME-PORT-005**: The game validator shall reject a `container/protocol` pair (protocol compared case-insensitively) that repeats within one game's `ports`, and a `tcp` or `udp` pair that another declared game already uses, excluding the game being edited from the sibling scan. (OpenSpec: game-port-visibility / Internal ports are ingressed from the VPC CIDR block only; Cross-game ICMP declarations)
- [x] **GAME-PORT-006**: While any game in the deployment has `https: true`, the game validator shall reject container port 443 or 80 with protocol `tcp` on every other game regardless of its visibility, identifying the HTTPS game that reserves it, in both edit orders (declaring the port first or enabling HTTPS first). (OpenSpec: game-port-visibility / Container ports 443 and 80 (tcp) are reserved deployment-wide when any game is HTTPS)
- [x] **GAME-PORT-007**: While no game in the deployment has `https: true`, the game validator shall accept container port 443 or 80 on `tcp`, and it shall accept 443 or 80 on `udp` regardless of HTTPS. (OpenSpec: game-port-visibility / Container ports 443 and 80 (tcp) are reserved deployment-wide when any game is HTTPS)
- [x] **GAME-PORT-008**: The add-game wizard and edit-game form shall let the operator set each port's visibility to Public or VPC-only, defaulting new ports to Public, persisting VPC-only as `visibility: 'internal'` and Public by omitting `visibility`. (OpenSpec: game-port-visibility / Wizard exposes per-port visibility)
- [x] **GAME-PORT-009**: The game model shall accept `protocol: 'icmp'` on a port entry, with `container` read as the ICMP type, and while a game is not HTTPS the game validator shall reject an ICMP type outside the integers 0 to 255, identifying the entry and stating the range. (OpenSpec: game-port-visibility / ICMP port declarations)
- [x] **GAME-PORT-010**: If a game with `https: true` declares an `icmp` port, then the game validator shall reject it through the HTTPS tcp/udp-only rule. (OpenSpec: game-port-visibility / ICMP port declarations)
- [x] **GAME-PORT-011**: For each game `icmp` port, the infra program shall declare a `game_servers` ingress rule with protocol `icmp`, `fromPort` equal to the type and `toPort` `-1`, sourced from `0.0.0.0/0` or the VPC CIDR by visibility, and shall add no ECS `portMappings` entry for it. (OpenSpec: game-port-visibility / ICMP port declarations)
- [x] **GAME-PORT-012**: The game validator shall permit the same `icmp` type on several games when every declaration has the same effective visibility, and the infra program shall emit one deduplicated rule for it; if two games declare the same `icmp` type with different effective visibility, then validation shall reject it naming both games. (OpenSpec: game-port-visibility / Cross-game ICMP declarations)
- [x] **GAME-PORT-013**: The game Networking step shall offer `tcp`, `udp` and `icmp` in each port row's protocol dropdown and, when `icmp` is selected on a blank row, shall prefill the field with 8, label it as the ICMP type with an "8 = echo request (ping)" hint, and block the step with "ICMP type must be an integer between 0 and 255" for an out-of-range value. (OpenSpec: game-port-visibility / Wizard supports ICMP entries)
- [x] **GAME-PORT-014**: When the infra program builds the Discord `GAME_PORTS` connect-port map, it shall skip `icmp` entries and use the first public non-`icmp` port for a non-HTTPS game, and shall map an HTTPS game to the public 443 URL form rather than `webPort` or any additional port. (OpenSpec: game-port-visibility / Connect-port surfaces exclude ICMP entries)
- [x] **GAME-PORT-015**: If a non-HTTPS game has non-`icmp` ports but none with public visibility, then the Discord `GAME_PORTS` map shall fall back to its first non-`icmp` port, internal or not. (observed: `infra/src/lambdas.ts:317-318`)

## Pinned Hostname

- [x] **GAME-HOST-001**: The game model shall accept an optional `pinnedHostname` string, the exact value `os.hostname()` returns inside that game's Node process, which carries no secret and round-trips unchanged through `deployment-config.json` and the redacted game shape. (OpenSpec: game-hostname-pinning (pending, `add-pinned-hostname`) / Optional pinned hostname field)
- [x] **GAME-HOST-002**: When a game without `pinnedHostname` is saved and read back, the system shall not synthesise a `pinnedHostname` key. (OpenSpec: game-hostname-pinning (pending) / Optional pinned hostname field)
- [x] **GAME-HOST-003**: If a game's `pinnedHostname` does not match `^[A-Za-z0-9]([A-Za-z0-9._-]{0,61}[A-Za-z0-9])?$`, then the game validator shall reject it with an issue at `pinnedHostname`, using the same pattern and message text in the wizard and the main process. (OpenSpec: game-hostname-pinning (pending) / Pinned hostname validation)
- [x] **GAME-HOST-004**: While a game declares `pinnedHostname`, the game validator shall reject a volume whose `container_path` is `/hyveon/hostname-shim` or under it (issue at that volume's `container_path`), a game named `hostname-shim` (issue at `name`), and a volume named `hostname-shim` (issue at that volume's `name`). (OpenSpec: game-hostname-pinning (pending) / Pinned hostname validation)
- [x] **GAME-HOST-005**: While a game declares no `pinnedHostname`, the game validator shall apply no hostname-shim name or path reservation to it. (OpenSpec: game-hostname-pinning (pending) / Pinned hostname validation)
- [x] **GAME-HOST-006**: Where a game declares `pinnedHostname`, the infra program shall add to that game's task definition only: a `<game>-hostname-shim` volume with no EFS configuration; a non-essential `hostname-shim` container on a pinned public busybox image that mounts the volume read-write at `/hyveon/hostname-shim` and writes `hostname-shim.js`, a CommonJS module replacing `require('node:os').hostname` with a function returning the configured value; and, on the game container, `dependsOn` `{ containerName: "hostname-shim", condition: "SUCCESS" }` plus a read-only mount of the volume at `/hyveon/hostname-shim`. (OpenSpec: game-hostname-pinning (pending) / Task definition wiring for a pinned hostname)
- [x] **GAME-HOST-007**: The pinned-hostname feature shall declare no resource outside the task definition, no ECS Service, and shall leave the Caddy sidecar definition identical to that of the same game without `pinnedHostname`.
