# Authoritative Health Check Specs

EARS requirements for prefix `RT-HEALTH`; design in `health-check-design.md` (same folder).

## Declaration and routing

- [x] **RT-HEALTH-DECL-001**: The `GameServerConfig` entry for a game in `deployment-config.json` shall accept an optional `healthCheck` declaration carrying a `kind` discriminator, whose only accepted value is `http`. (OpenSpec: game-health-checks / A game may declare an authoritative health check)
- [x] **RT-HEALTH-DECL-006**: The health-check Lambda shall return a verdict of shape `{ active: boolean, reason: string, failureDerived: boolean }` for every invocation it completes. (observed)

## HTTP request

- [x] **RT-HEALTH-HTTP-001**: When the health-check Lambda runs an `http`-kind check, it shall issue one HTTP request to `{scheme}://{taskPrivateIp}:{port}{path}` using the declared method, the declared headers, and the declared `timeoutMs` as a single wall-clock budget for the whole request. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-HTTP-002**: When the health-check Lambda runs an `http`-kind check, it shall take the destination host only from the checked task's private IPv4 address as reported by ECS `DescribeTasks`, and no `healthCheck` field shall be capable of supplying or overriding the host. (OpenSpec: game-health-checks / Reaching into a game task is confined to what the configuration declares)
- [x] **RT-HEALTH-HTTP-003**: The health-check Lambda shall not follow HTTP redirects when issuing an `http`-kind check, so a 3xx response is evaluated as a non-successful status. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-HTTP-004**: When the health-check Lambda resolves the host and the credential for one check, it shall perform the ECS lookup and the Secrets Manager lookup concurrently. (observed)
- [ ] **RT-HEALTH-HTTP-005**: Where an `http`-kind check declares `scheme: 'https'`, the health-check Lambda shall complete the TLS handshake with the task's Caddy sidecar despite addressing the task by private IP rather than by its certificate hostname. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition) (gap: `app/packages/lambda/health-check/src/handler.ts:165-172` sends the request to an IP with default certificate validation; untested and appears to fail hostname verification)

## Credential injection

- [x] **RT-HEALTH-AUTH-001**: When a health check's `auth` declares `type: 'raw'` or no `type`, the health-check Lambda shall set the `Authorization` header to the resolved secret string verbatim with no added prefix. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-AUTH-002**: When a health check's `auth` declares `type: 'bearer'`, the health-check Lambda shall set the `Authorization` header to `Bearer ` followed by the resolved secret string. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-AUTH-003**: When a health check's `auth` declares `type: 'basic'`, the health-check Lambda shall parse the resolved secret as a JSON object with string `username` and `password` and set the `Authorization` header to `Basic ` followed by the base64 encoding of `username:password`. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-AUTH-004**: If a `type: 'basic'` health-check secret is not valid JSON or lacks string `username` and `password` fields, then the health-check Lambda shall treat the credential as unavailable and return a failure-derived active verdict. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-AUTH-005**: When a health check declares `auth` and its declared `headers` also contain a key equal to `authorization` case-insensitively, the health-check Lambda shall discard the declared header and send only the constructed `Authorization` header. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-AUTH-006**: The health-check Lambda shall place the constructed `Authorization` value only in the `Authorization` request header, never in the request path, query string, or any other header. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)

## Verdict evaluation

- [x] **RT-HEALTH-EVAL-001**: The health-check verdict engine (`evaluateHealthCheck`) shall be a pure function of the declaration, the HTTP status and the raw response body, with no I/O. (observed)
- [x] **RT-HEALTH-EVAL-002**: When a health-check response has a 2xx status and a JSON body whose scalar value at the declared `jsonPath` satisfies the declared operator, the verdict engine shall return `active: true` with `failureDerived: false`. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-EVAL-003**: When a health-check response has a 2xx status and a JSON body whose scalar value at the declared `jsonPath` does not satisfy the declared operator, the verdict engine shall return `active: false` with `failureDerived: false`. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-EVAL-004**: When a health check declares the `exists` operator and the response is a 2xx JSON body, the verdict engine shall return active if the declared `jsonPath` resolves to any value and idle (not failure-derived) if it does not. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-EVAL-005**: The verdict engine shall resolve `jsonPath` as a restricted dialect of dotted field names and numeric array indices only, where any other syntax resolves no value. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-EVAL-006**: When the verdict engine applies `equals` or `notEquals`, it shall treat a resolved and declared value of different JSON types as incomparable, except that a `null` on either side compares by identity without a type check. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition; the `null` exemption is observed in `app/packages/lambda/health-check/src/engine.ts:117` and is not stated in OpenSpec)
- [x] **RT-HEALTH-EVAL-007**: When the verdict engine applies `greaterThan` or `lessThan`, it shall compare numerically, accepting numeric strings, and treat a value that does not parse to a finite number as incomparable. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-EVAL-008**: When the verdict engine applies `contains`, it shall test substring containment and treat a non-string resolved or declared value as incomparable. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-EVAL-009**: The verdict engine's `reason` text shall name only the declared `jsonPath`, the operator, or the HTTP status, and shall never include the resolved response value or any part of the response body. (OpenSpec: game-health-checks / The basis for a shutdown decision is recoverable from the logs)

## Fail-active

- [x] **RT-HEALTH-FAIL-001**: If a health-check response status is outside 200-299, then the verdict engine shall return a failure-derived active verdict. (OpenSpec: game-health-checks / A failed check reports the server as active)
- [x] **RT-HEALTH-FAIL-002**: If a health-check response body is not valid JSON, then the verdict engine shall return a failure-derived active verdict. (OpenSpec: game-health-checks / A failed check reports the server as active)
- [x] **RT-HEALTH-FAIL-003**: If, for any operator other than `exists`, the declared `jsonPath` resolves no value, resolves an object or array, or resolves a value the operator cannot compare, then the verdict engine shall return a failure-derived active verdict. (OpenSpec: game-health-checks / A failed check reports the server as active)
- [x] **RT-HEALTH-FAIL-004**: If the health-check Lambda's ECS lookup, secret fetch, credential construction, connection, or request timeout fails, then the Lambda shall return `active: true`, `failureDerived: true`, and a reason prefixed `health check failed:`. (OpenSpec: game-health-checks / A failed check reports the server as active)

## Provisioning and runtime environment

- [x] **RT-HEALTH-PROV-001**: While no game in `deployment-config.json` declares `healthCheck`, infra shall declare no health-check Lambda, log group, IAM role, IAM policy, or security group, and shall grant the watchdog no `lambda:InvokeFunction` statement. (OpenSpec: game-health-checks / Health checking is provisioned only for games that use it)
- [x] **RT-HEALTH-PROV-002**: While at least one game declares `healthCheck`, infra shall declare exactly one `{projectName}-health-check` Lambda, one role, and one security group serving every opted-in game. (OpenSpec: game-health-checks / Health checking is provisioned only for games that use it)
- [ ] **RT-HEALTH-PROV-003**: While at least one game declares `healthCheck`, infra shall provide the health-check Lambda with every environment variable its handler requires at module load, including `ECS_CLUSTER`. (observed) (gap: `app/packages/lambda/health-check/src/handler.ts:39` requires `ECS_CLUSTER`; `app/packages/infra/src/lambdas.ts:552` sets only `AWS_REGION_`, pinned by `app/packages/infra/src/lambdas.test.ts:792`)
- [ ] **RT-HEALTH-PROV-004**: While at least one game declares `healthCheck`, the deployed health-check Lambda shall have a network path and security-group egress to the ECS and Secrets Manager APIs from its VPC placement. (observed) (gap: `app/packages/infra/src/lambdas.ts:548-551` places it in public subnets with no NAT or endpoints in `app/packages/infra/src/network.ts`; its SG egress is only game ports toward `gameServersSg`, `app/packages/infra/src/securityGroups.ts:430-446`)
- [ ] **RT-HEALTH-PROV-005**: The health-check package's tests shall fail when the handler requires an env var that infra does not provision. (observed) (gap: `app/packages/lambda/health-check/src/handler.test.ts:18-20` sets `ECS_CLUSTER` before import, masking RT-HEALTH-PROV-003)
- [x] **RT-HEALTH-PROV-006**: The health-check Lambda shall read its region from `AWS_REGION_` (trailing underscore), falling back to `AWS_REGION`, `AWS_DEFAULT_REGION`, then `us-east-1`. (observed; CLAUDE.md invariant)

## Network and permission confinement

- [x] **RT-HEALTH-NET-001**: While at least one game declares `healthCheck`, the health-check security group shall carry one TCP egress rule per distinct declared health-check port toward `gameServersSg` and no other egress, and `gameServersSg` shall carry a matching ingress rule from the health-check security group per port. (OpenSpec: game-health-checks / Reaching into a game task is confined to what the configuration declares)
- [x] **RT-HEALTH-NET-002**: The health-check Lambda's IAM policy shall grant `ecs:DescribeTasks` only on tasks in the deployment's ECS cluster and `secretsmanager:GetSecretValue` only on the `auth.secretArn` values persisted by opted-in games, plus logging and VPC ENI permissions. (OpenSpec: game-health-checks / Reaching into a game task is confined to what the configuration declares)
- [x] **RT-HEALTH-NET-003**: The health-check Lambda shall have no Function URL, and the only `lambda:InvokeFunction` grant on it shall be in the watchdog's role policy. (OpenSpec: game-health-checks / Reaching into a game task is confined to what the configuration declares)
- [x] **RT-HEALTH-NET-004**: The watchdog Lambda shall have no VPC attachment and no Secrets Manager permission for health-check credentials. (OpenSpec: game-health-checks / Reaching into a game task is confined to what the configuration declares)
- [x] **RT-HEALTH-NET-005**: The persisted `healthCheck.auth` in `deployment-config.json` shall carry only a `type` and a Secrets Manager `secretArn`, never a credential value. (OpenSpec: game-health-checks / Reaching into a game task is confined to what the configuration declares)

## Save-time validation

- [x] **RT-HEALTH-VALID-001**: When an operator saves a game whose `healthCheck.port` is neither one of the game's declared TCP container ports nor its `webPort`, the game-server validator shall reject the save with an issue at `healthCheck.port`. (OpenSpec: game-health-checks / Health-check configuration is validated before it is saved)
- [x] **RT-HEALTH-VALID-002**: When an operator saves a health check whose `path` is empty or does not start with `/`, the game-server validator shall reject the save. (OpenSpec: game-health-checks / Health-check configuration is validated before it is saved)
- [x] **RT-HEALTH-VALID-003**: When an operator saves a health check whose `timeoutMs` is not an integer between 100 and 10000 inclusive, the game-server validator shall reject the save. (OpenSpec: game-health-checks / Health-check configuration is validated before it is saved)
- [x] **RT-HEALTH-VALID-004**: When an operator saves a health check with an operator other than `exists` and no `activeWhen.value`, or with `exists` and a `value`, the game-server validator shall reject the save. (OpenSpec: game-health-checks / Health-check configuration is validated before it is saved)
- [x] **RT-HEALTH-VALID-005**: When an operator saves a health check using `greaterThan` or `lessThan` with a non-number `value`, or `contains` with a non-string `value`, the game-server validator shall reject the save. (observed)
- [x] **RT-HEALTH-VALID-006**: When an operator saves a health check whose `activeWhen.jsonPath` does not match `^[A-Za-z0-9_]+(\.[A-Za-z0-9_]+|\[\d+\])*$` (which excludes a leading `$`), the game-server validator shall reject the save. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-VALID-007**: When an operator saves a health check whose declared `headers` contain an `authorization` key or a value resembling a bearer token, basic-auth pair, or long API-key string, the game-server validator shall reject the save. (OpenSpec: game-health-checks / The HTTP check kind evaluates a declared request against a declared condition)
- [x] **RT-HEALTH-VALID-008**: When an operator saves a health-check credential with `type: 'basic'` lacking a username or password, `type: 'bearer'` lacking a token, or `type: 'raw'` (or no type) lacking a Secrets Manager ARN matching `arn:aws:secretsmanager:<region>:<account>:secret:<name>`, the write-input validator shall reject the save. (OpenSpec: game-health-checks / Health-check configuration is validated before it is saved)

## Logging

- [x] **RT-HEALTH-LOG-001**: When the health-check Lambda produces a verdict, it shall log one structured line carrying `game`, `kind`, `active` and `reason`, at `warn` when the verdict is failure-derived and at `debug` otherwise. (OpenSpec: game-health-checks / The basis for a shutdown decision is recoverable from the logs)
- [x] **RT-HEALTH-LOG-002**: When the watchdog receives a failure-derived health-check verdict, it shall log a `warn` line naming the game and the reason. (OpenSpec: game-health-checks / The basis for a shutdown decision is recoverable from the logs)
- [x] **RT-HEALTH-LOG-003**: When the watchdog counts a health-checked task as idle, it shall log the idle count together with the health-check verdict's reason, so a later shutdown is attributable to the sequence of check outcomes. (OpenSpec: game-health-checks / The basis for a shutdown decision is recoverable from the logs)
- [x] **RT-HEALTH-LOG-004**: The health-check Lambda's and the watchdog's health-check log lines shall never contain a credential value or any part of a response body. (OpenSpec: game-health-checks / The basis for a shutdown decision is recoverable from the logs)

## Operator interface redaction

- [x] **RT-HEALTH-REDACT-001**: When a game with a `healthCheck` is sent to the renderer, `redactGameServer` shall replace `healthCheck.auth` with `secretSet` (whether a credential is configured) and `authType` (the credential type, `raw` when absent), and shall send no ARN, username, password, or token. (OpenSpec: game-health-checks / Health-check credentials never reach the operator interface)
- [x] **RT-HEALTH-REDACT-002**: While the add/edit-game wizard shows a game whose health check has `secretSet: true`, the wizard's health-check fields shall indicate that a credential is set and leave the credential inputs empty, so a blank input keeps the existing credential. (OpenSpec: game-health-checks / Health-check credentials never reach the operator interface)
- [x] **RT-HEALTH-REDACT-003**: The wizard's health-check fields shall offer auth types `none`, `raw`, `basic` and `bearer`, render the password and token inputs as masked fields, and offer the game's `webPort` as a selectable target port ahead of its extra TCP ports. (observed)
- [ ] **RT-HEALTH-REDACT-004**: When a save is rejected with an issue at `healthCheck.timeoutMs`, the wizard's health-check fields shall display that issue's message beside the timeout input. (observed) (gap: `app/packages/web/src/components/add-game-wizard/health-check-fields.component.tsx:122` passes no `errors` prop to the timeout `FormField`)

## App-owned credential lifecycle

- [x] **RT-HEALTH-CRED-001**: When an operator saves a `type: 'basic'` or `type: 'bearer'` health-check credential, the game write path shall store the credential (`{ username, password }` JSON for basic, the raw token for bearer) in an app-owned Secrets Manager secret named `hyveon-{gameId}-healthcheck-auth` and persist only that secret's ARN. (OpenSpec: game-health-checks / App-owned health-check credentials are provisioned and retired by the app)
- [x] **RT-HEALTH-CRED-002**: When the app-owned health-check secret for a game already exists, `upsertHealthCheckAuthSecret` shall update its value in place with `PutSecretValue` and shall not create another secret. (OpenSpec: game-health-checks / App-owned health-check credentials are provisioned and retired by the app)
- [x] **RT-HEALTH-CRED-003**: If `PutSecretValue` on the app-owned health-check secret fails because the secret is scheduled for deletion (confirmed by `DescribeSecret.DeletedDate`), then `upsertHealthCheckAuthSecret` shall restore the secret and retry the put once. (observed)
- [x] **RT-HEALTH-CRED-004**: If `PutSecretValue` on the app-owned health-check secret fails with `ResourceNotFoundException`, then `upsertHealthCheckAuthSecret` shall create the secret. (observed)
- [x] **RT-HEALTH-CRED-005**: When an operator clears a `basic` or `bearer` health-check credential, switches it to `raw`, removes the `healthCheck`, or deletes the game, the game write path shall delete the app-owned secret using the default recovery window. (OpenSpec: game-health-checks / App-owned health-check credentials are provisioned and retired by the app)
- [x] **RT-HEALTH-CRED-006**: When an operator removes a `type: 'raw'` (or untyped) health-check credential or deletes a game that declares one, the game write path shall not delete the referenced Secrets Manager secret. (OpenSpec: game-health-checks / App-owned health-check credentials are provisioned and retired by the app)
- [x] **RT-HEALTH-CRED-007**: If deleting an app-owned health-check secret fails, then the game write path shall log a `warn` and still complete the config write, and if creating or updating it fails, then the write path shall log an `error` and reject the save with a plain `Error`. (observed)
- [x] **RT-HEALTH-CRED-008**: The `HyveonDeployAll` deploy policy evaluated by the Settings account check shall grant `secretsmanager:*`, covering creation, update, restore, and deletion of app-owned health-check secrets. (OpenSpec: game-health-checks / App-owned credential lifecycle requires no additional account permission)

## Dropped from OpenSpec
