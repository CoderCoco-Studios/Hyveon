# Game Task Lifecycle and DNS Specs

EARS requirements for prefix `RT-TASK`; design in `docs/intent/game-runtime/task-and-dns/task-and-dns-design.md`.

## Start and Stop

- [x] **RT-TASK-LAUNCH-001**: The desktop app shall start a game server only by issuing one ECS `RunTask` with `count: 1` against the game's `{game}-server` task definition, and shall never create or scale a persistent ECS Service. (observed: `AwsCloudProvider.ts:432-443`; CLAUDE.md invariant "No persistent ECS Service")
- [x] **RT-TASK-LAUNCH-002**: When the desktop app starts a game server, the `RunTask` request shall use the `FARGATE` launch type, the stack-output subnets and security group, and `assignPublicIp: ENABLED`. (observed: `AwsCloudProvider.ts:432-443`, `EcsService.ts:64-81`)
- [x] **RT-TASK-LAUNCH-003**: When the desktop app starts a game server via `AwsCloudProvider.startWorkload`, the `RunTask` request shall set `propagateTags: 'TASK_DEFINITION'` so the running task inherits the task definition's `Game` tag. (OpenSpec: cost-visibility / Running ECS tasks propagate the Game tag from their task definition)
- [x] **RT-TASK-LAUNCH-004**: When the Discord followup Lambda starts a game server via `RunTask` in response to `/server-start`, the request shall set `propagateTags: 'TASK_DEFINITION'` so the running task inherits the task definition's `Game` tag. (OpenSpec: cost-visibility / Running ECS tasks propagate the Game tag from their task definition; code in `followup/src/handler.ts:136`)
- [x] **RT-TASK-LAUNCH-005**: If a desktop Start is requested for a game while a non-stopped task for that game's `{game}-server` family exists, then the desktop app shall refuse without calling `RunTask` and report `"{game} is already running."`. (observed: `AwsCloudProvider.ts:424-425`)
- [x] **RT-TASK-LAUNCH-006**: If a desktop Stop is requested for a game with no non-stopped task, then the desktop app shall refuse without calling `StopTask` and report `"{game} is not currently running."`. (observed: `AwsCloudProvider.ts:476`)
- [x] **RT-TASK-LAUNCH-007**: When the desktop app stops a game server, it shall call `StopTask` on the game's active task with reason `Stopped via management app` and shall perform no DNS change itself, leaving record cleanup to the update-dns Lambda's STOPPED path. (observed: `AwsCloudProvider.ts:457-484`; CLAUDE.md invariant "DNS records are Lambda-managed")
- [x] **RT-TASK-LAUNCH-008**: While no stack outputs exist, the desktop app shall refuse Start with `"Infrastructure is not deployed. Run Apply on the IaC page first."` and Stop with `"Infrastructure is not deployed."`. (observed: `AwsCloudProvider.ts:413-414,464-465`, `EcsService.ts:69`)
- [x] **RT-TASK-LAUNCH-009**: Within one desktop-app process, `AwsCloudProvider` shall serialise start and stop calls for the same game in call order, while calls for different games run concurrently, and a failed call shall not block the next queued call for that game. (observed: `AwsCloudProvider.ts:319-336`)
- [ ] **RT-TASK-LAUNCH-010**: If a desktop Start and a Discord `/server-start` for the same game overlap, then the system shall launch at most one task for that game. (gap: `withGameLock` is in-process only, `AwsCloudProvider.ts:328-336`; the followup Lambda's `RunTask` at `followup/src/handler.ts:127-138` is unguarded by it)
- [x] **RT-TASK-LAUNCH-011**: If `RunTask` returns no tasks, then the desktop app shall report `"Failed to start {game}: {reason}"` using the first ECS failure reason, or `unknown` when none is given. (observed: `AwsCloudProvider.ts:444-449`)
- [x] **RT-TASK-LAUNCH-012**: When a desktop Start succeeds, `EcsService.start` shall return `success: true`, the task ARN, and the message `"{game} is starting. It may take 2–5 minutes."`; when a desktop Stop succeeds, `EcsService.stop` shall return `success: true` and `"{game} is stopping."`. (observed: `EcsService.ts:316-356`)
- [x] **RT-TASK-LAUNCH-013**: If a desktop Start or Stop fails with a guard refusal or launch failure, then `EcsService` shall return `success: false` with the provider's message unprefixed; for any other error it shall return `String(err)`. (observed: `EcsService.ts:122-125,327-332,347-354`)
- [ ] **RT-TASK-LAUNCH-014**: If a desktop Start or Stop fails with a non-guard error, then `EcsService` shall log the normalised error message rather than the raw error object. (gap: `EcsService.ts:330,352` log `{ err }`; `.claude/rules/logging.md` rule 2)

## Status

- [x] **RT-TASK-STATUS-001**: While no stack outputs exist, the desktop app's workload status for any game shall be `not_deployed` with message `"Run Apply on the IaC page first."`. (observed: `AwsCloudProvider.ts:505-506`)
- [x] **RT-TASK-STATUS-002**: When a game's non-stopped task has `lastStatus` `RUNNING`, the desktop app's status shall be `running` with the task ARN, the ENI's public IP when it resolves, and hostname `{game}.{domain}` when a domain is configured. (observed: `AwsCloudProvider.ts:510-520`)
- [x] **RT-TASK-STATUS-003**: When a game's non-stopped task has any `lastStatus` other than `RUNNING`, `STOPPED` or `DEPROVISIONING`, the desktop app's status shall be `starting` with the task ARN. (observed: `AwsCloudProvider.ts:365-370,522`)
- [x] **RT-TASK-STATUS-004**: When no non-stopped task exists for a game's `{game}-server` family, the desktop app's status shall be `stopped`. (observed: `AwsCloudProvider.ts:524`)
- [x] **RT-TASK-STATUS-005**: If resolving one game's status throws, including during credential or config resolution, then the desktop app shall report `error` with `String(err)` for that game only, without failing the status read for other games. (observed: `AwsCloudProvider.ts:494-499,525-527`)
- [x] **RT-TASK-STATUS-006**: If the ENI public-IP lookup fails for a running task, then the desktop app shall report `running` without a public IP and log the failure through the injected logger. (observed: `AwsCloudProvider.ts:388-398`, `EcsService.ts:92-94`)
- [x] **RT-TASK-STATUS-007**: `EcsService.getStatus` shall map a `WorkloadStatus` onto the `GameStatus` shape by passing through `state`, `publicIp`, `hostname` and `message` and renaming `workloadId` to `taskArn`. (observed: `EcsService.ts:295-306`)
- [ ] **RT-TASK-STATUS-008**: The `GameStatus`, `StartResult` and `CostEstimates` shapes shall be declared once in `@hyveon/shared` and imported by `desktop-main`, `desktop-preload` and `web`. (gap: redeclared at `EcsService.ts:148,162`, `CostService.ts:14`, `desktop-preload/src/hyveon-api.ts:100,126`, `web/src/api.service.ts:121,147`)
- [ ] **RT-TASK-STATUS-009**: The desktop app shall use a single region source for every ECS call it makes, covering start, stop, status, the cost-estimate task-definition describe and the helper-task ECS helpers. (gap: provider uses `outputs.awsRegion` at `EcsService.ts:72`; `EcsService.getClient` uses `ConfigService.getRegion()` at `EcsService.ts:214`)

## DNS Lifecycle

- [x] **RT-TASK-DNS-001**: The infra program shall declare no per-game DNS record; the update-dns Lambda shall be the only writer of `{game}.{domain}` A records. (observed: CLAUDE.md invariant; `update-dns/src/handler.ts:98-170`; `infra/src/route53.ts` declares a hosted-zone lookup only)
- [x] **RT-TASK-DNS-002**: The update-dns Lambda shall be invoked by an EventBridge rule matching `aws.ecs` `ECS Task State Change` events for this deployment's cluster ARN with `lastStatus` `RUNNING` or `STOPPED`. (observed: `infra/src/lambdas.ts:660-675`)
- [x] **RT-TASK-DNS-003**: When the update-dns Lambda receives an event whose `detail.group` family is not a configured `{game}-server` family, including the helper task's family, it shall return `skipped` and make no Route 53 or Discord call. (observed: `update-dns/src/handler.ts:257-263`)
- [x] **RT-TASK-DNS-004**: When the update-dns Lambda receives a RUNNING event for a game task, it shall resolve the task's public IP from its ENI with up to five attempts spaced 3 s apart before giving up. (observed: `update-dns/src/handler.ts:71-96`)
- [x] **RT-TASK-DNS-005**: When the update-dns Lambda resolves a RUNNING game task's public IP, it shall UPSERT an A record `{game}.{DOMAIN_NAME}` to that IP with TTL `DNS_TTL`. (observed: `update-dns/src/handler.ts:98-118,231`)
- [x] **RT-TASK-DNS-006**: If the update-dns Lambda cannot resolve a RUNNING game task's public IP, then it shall make no Route 53 change and return `no_ip`. (observed: `update-dns/src/handler.ts:224-229`)
- [x] **RT-TASK-DNS-007**: When the update-dns Lambda receives a STOPPED event for a game task and an A record `{game}.{DOMAIN_NAME}` exists, it shall issue a Route 53 DELETE for that record. (observed: `update-dns/src/handler.ts:141-166,235-238`)
- [x] **RT-TASK-DNS-008**: When the update-dns Lambda receives a STOPPED event for a game task and no A record `{game}.{DOMAIN_NAME}` exists, it shall log and return without a Route 53 change. (observed: `update-dns/src/handler.ts:142-146`)
- [ ] **RT-TASK-DNS-009**: When the update-dns Lambda deletes a game's A record on STOPPED, the DELETE shall carry the existing record's TTL and value as read from Route 53, so a `dnsTtl` change between UPSERT and DELETE cannot leave the record behind. (gap: `update-dns/src/handler.ts:159` sends the current `DNS_TTL`)
- [ ] **RT-TASK-DNS-010**: If a STOPPED event arrives for a game task whose public IP differs from the IP in the game's current A record, then the update-dns Lambda shall leave the record in place. (gap: no ownership check at `update-dns/src/handler.ts:141-166,235-238`)
- [x] **RT-TASK-DNS-011**: HTTPS game tasks (Caddy sidecar, `https: true`) shall use the same update-dns A-record path as every other game: UPSERT to the task's public IP on RUNNING and DELETE on STOPPED. (OpenSpec: in-task-tls-termination / HTTPS games use the Lambda-managed DNS lifecycle; `update-dns/src/handler.ts:217-240`)
- [x] **RT-TASK-DNS-012**: The update-dns Lambda source and its wiring in `infra/src/lambdas.ts` shall contain no ELBv2 API call, no `ALB_TARGET_GROUPS` or `HTTPS_GAMES` environment variable, and no `elasticloadbalancing` IAM statement. (OpenSpec: in-task-tls-termination / HTTPS games use the Lambda-managed DNS lifecycle)
- [x] **RT-TASK-DNS-013**: The update-dns Lambda shall read its region from `AWS_REGION_` first, falling back to `AWS_REGION`, `AWS_DEFAULT_REGION`, then `us-east-1`. (observed: `update-dns/src/handler.ts:51-59`; CLAUDE.md invariant "Lambda env vars use `AWS_REGION_`")
- [ ] **RT-TASK-DNS-014**: The update-dns Lambda shall log identifiers from each EventBridge event (task ARN, family, `lastStatus`) rather than the full event JSON. (gap: `update-dns/src/handler.ts:252`)
- [x] **RT-TASK-DNS-015**: The shared ENI helpers (`getTaskEniId`, `getTaskPrivateIp`, `resolveEniPublicIp` in `@hyveon/shared/aws/ecsTask`) shall use structural types and a caller-supplied `DescribeNetworkInterfaces` callback, importing no `@aws-sdk/*` package. (observed: `shared/src/aws/ecsTask.ts:1-16,68-107`; CLAUDE.md invariant on the shared barrel)

## Discord Follow-up on Task State

- [x] **RT-TASK-NOTIFY-001**: Where the update-dns Lambda's `TABLE_NAME` is set, when it UPSERTs a RUNNING game task's record and a `PENDING#{taskArn}` row exists, it shall PATCH that Discord interaction with the formatted running status (hostname, IP, per-game connect message and port) and delete the row. (observed: `update-dns/src/handler.ts:176-198,232`)
- [x] **RT-TASK-NOTIFY-002**: Where the update-dns Lambda's `TABLE_NAME` is set, if a RUNNING game task's public IP cannot be resolved and a `PENDING#{taskArn}` row exists, then it shall PATCH that interaction with an error status and delete the row. (observed: `update-dns/src/handler.ts:187-193,224-228`)
- [x] **RT-TASK-NOTIFY-003**: Where the update-dns Lambda's `TABLE_NAME` is empty, it shall skip every pending-interaction lookup. (observed: `update-dns/src/handler.ts:181`)
- [x] **RT-TASK-NOTIFY-004**: If the update-dns Lambda's Discord PATCH or pending-row delete fails, then it shall log the failure and still return the DNS result. (observed: `update-dns/src/handler.ts:195-197`)
- [ ] **RT-TASK-NOTIFY-005**: Where the update-dns Lambda's `TABLE_NAME` is set, when a STOPPED event arrives for a game task with a `PENDING#{taskArn}` row (a task that stopped before reaching RUNNING), it shall PATCH the interaction with an error status and delete the row. (gap: STOPPED path never consults the row, `update-dns/src/handler.ts:235-238`)
- [ ] **RT-TASK-NOTIFY-006**: If the update-dns Lambda's RUNNING-path UPSERT fails and a `PENDING#{taskArn}` row exists, then it shall PATCH the interaction with an error status before failing the invocation. (gap: no try around `upsertDns`, `update-dns/src/handler.ts:231-232`)

## Cost Estimates

- [x] **RT-TASK-COST-001**: The app shall not make any AWS Cost Explorer API request, including `GetCostAndUsage`, from any code path, automatic or user-triggered. (OpenSpec: cost-visibility / No AWS Cost Explorer API calls)
- [x] **RT-TASK-COST-002**: No `CloudProvider` implementation, desktop-main service, controller or IPC channel shall expose a method that calls the AWS Cost Explorer API. (OpenSpec: cost-visibility / No AWS Cost Explorer API calls)
- [x] **RT-TASK-COST-003**: When an operator navigates to the Dashboard route (`/`), on that or any later mount, the app shall make no AWS Cost Explorer API request. (OpenSpec: cost-visibility / No AWS Cost Explorer API calls, scenario "Navigating to the Dashboard")
- [x] **RT-TASK-COST-004**: When an operator navigates to the Costs page (`/costs`), the app shall make no AWS Cost Explorer API request. (OpenSpec: cost-visibility / No AWS Cost Explorer API calls, scenario "Navigating to the Costs page")
- [x] **RT-TASK-COST-005**: While an operator navigates between the Dashboard and Costs page any number of times in a session, the app's cumulative AWS Cost Explorer request count shall remain zero. (OpenSpec: cost-visibility / No AWS Cost Explorer API calls, scenario "Repeated navigation over a session")
- [x] **RT-TASK-COST-006**: The `costs.estimate` IPC channel shall derive each configured game's estimate only from its `{game}-server` task-definition CPU/memory (via `DescribeTaskDefinition`) and the static Fargate on-demand constants `FARGATE_VCPU_PER_HOUR` and `FARGATE_GB_PER_HOUR`. (OpenSpec: cost-visibility / Free per-game Fargate cost estimates; `costs.controller.ts:28-48`, `CostService.ts:31-42`)
- [x] **RT-TASK-COST-007**: The `costs.estimate` IPC channel shall return, per game, `vcpu` (cpu/1024), `memoryGb` (memory/1024), `costPerHour` (4 decimals), `costPerDay24h` (hourly × 24, 2 decimals) and `costPerMonth4hpd` (hourly × 4 × 30, 2 decimals), plus `totalPerHourIfAllOn` as the sum of `costPerHour`. (observed: `CostService.ts:31-42`, `costs.controller.ts:42-47`)
- [x] **RT-TASK-COST-008**: While no stack outputs exist, the `costs.estimate` IPC channel shall return `{ games: {}, totalPerHourIfAllOn: 0 }`. (observed: `costs.controller.ts:31-34`)
- [x] **RT-TASK-COST-009**: When the Costs page loads and Cost Explorer has never been called, the per-game estimates table shall render `$/hour`, `$/day` and `$/month` figures for every configured game. (OpenSpec: cost-visibility / Free per-game Fargate cost estimates, scenario "Per-game estimates table renders without any actual-cost data"; `costs.page.tsx:296-298`)
- [ ] **RT-TASK-COST-010**: The desktop app shall compute a Fargate hourly cost from CPU/memory through one shared function, used by the wizard estimate, `CostService` and `AwsCloudProvider`. (gap: three copies at `shared/src/gameServerValidator.ts:426-431`, `CostService.ts:31-42`, `AwsCloudProvider.ts:312-317`)
- [ ] **RT-TASK-COST-011**: If a game's task-definition CPU or memory is missing or its describe fails, then every desktop cost-estimate path shall apply the same fallback CPU/memory values. (gap: 1024/2048 at `EcsService.ts:372-373` vs 2048/8192 at `costs.controller.ts:39` and `AwsCloudProvider.ts:297-302`)
- [ ] **RT-TASK-COST-012**: The `costs.estimate` IPC channel and `CloudProvider.getCostEstimate` shall share one implementation, or `getCostEstimate` shall be removed from the `CloudProvider` interface. (gap: `getCostEstimate` at `shared/src/cloud.ts:55`, `AwsCloudProvider.ts:603-623` has no production caller; `costs.controller.ts:37-39` bypasses it)

## Dropped from OpenSpec

These `cost-visibility` scenarios are current and implemented, but their behaviour is owned by another leaf, so they are not carried as `RT-TASK` specs.

- cost-visibility / Free per-game Fargate cost estimates, scenario "Live estimate updates as resources are selected": the wizard estimate is `estimateFargateHourlyCost` in the `game-server` leaf (`shared/src/gameServerValidator.ts:426-431`).
- cost-visibility / Free per-game Fargate cost estimates, scenario "Live estimate available before the game server is saved": same owner, `game-server`.
- cost-visibility / Per-game AWS resources carry a Game cost allocation tag, scenario "ECS task definition tagged per game": provisioned by the `iac/program` leaf.
- cost-visibility / Per-game AWS resources carry a Game cost allocation tag, scenario "Per-game CloudWatch log group tagged per game": `iac/program`.
- cost-visibility / Per-game AWS resources carry a Game cost allocation tag, scenario "EFS-seeder Lambda tagged per game": `iac/program`.
- cost-visibility / Per-game AWS resources carry a Game cost allocation tag, scenario "Shared resources are not tagged per game": `iac/program`.
