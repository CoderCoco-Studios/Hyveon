# Lens candidates for segmenting Hyveon (Phase-2)

Five fundamentally different clusterings, each grounded in the sweep reports and the inventory (`inventory.md`, row numbers in parentheses refer to its functional-unit table). File counts are approximate and include co-located tests (657 tracked files under `app/packages`; ~245 renderer, ~190 desktop-main, ~75 shared, ~20 cloud-aws, ~7 preload, ~37 infra, ~34 lambda, ~70 e2e/config). `pkg/` abbreviates `app/packages/`.

Two cross-cutting observations first, because every lens has to deal with them:

- **There is no OpenSpec capability for the Discord bot.** Interactions, followup, `canRun`, command registration, the config page and the `discord.{zone}` domain are covered only by CLAUDE.md invariants, `docs/docs/app/discord.md`, and fragments inside `cost-visibility`, `game-port-visibility` (GAME_PORTS) and `pulumi-infra-program` (secret placeholders). Any LID clustering will create the first explicit home for it.
- **Carrier code has no purpose of its own.** `preload.ts`/`hyveon-api.ts` (82), `ipc-main-bridge.ts` (80), `components/ui/*` (5), `app.module.ts`/modules (81), `electron.vite.config.ts`/`electron-builder.yml` (90) exist to carry other clusters. Every lens below is tempted to make a "platform/plumbing" cluster out of them, which is the frontend/backend/deploy-unit grouping the brief forbids. Each lens states how it avoids that.

## Clustering A: Data-flow — "follow the datum"

**Lens**: Group code by the piece of data that is born, transformed and consumed along one path, regardless of which process or package touches it.

**Clusters it produces** (8):

1. **declared-desired-state** — The operator's description of what should exist: a game or setting is typed, validated, written as a versioned `deployment-config.json`, and compared against what was last applied; covering ~105 files incl. `pkg/shared/src/gameServerValidator.ts`, `pkg/web/src/components/add-game-wizard/add-game-wizard.component.tsx`, `pkg/desktop-main/src/services/GamesWriteService.ts`, `pkg/desktop-main/src/services/DeploymentConfigService.ts`, `pkg/cloud-aws/src/AwsRemoteFileStore.ts`, `pkg/desktop-main/src/services/DriftService.ts` (rows 10–18, 24–26, 28, 46).
2. **plan-to-stack-materialisation** — A plan artifact becomes an approved, hash-gated apply that produces stack outputs and a durable run record; covering ~125 files incl. `pkg/desktop-main/src/services/PulumiService.ts`, `pkg/infra/src/program.ts`, `pkg/desktop-main/src/services/RunService.ts`, `pkg/cloud-aws/src/AwsRunRecordStore.ts`, `pkg/web/src/pages/iac.page.tsx` (rows 34–44, 47–53, 77). **Warning: fat** (>120 files); the infra definers alone are 37 files.
3. **task-state-and-dns-propagation** — A RunTask call turns into an ECS task, an EventBridge event, a Route 53 record, a polled status and eventually a watchdog stop; covering ~40 files incl. `pkg/cloud-aws/src/AwsCloudProvider.ts`, `pkg/lambda/update-dns/src/handler.ts`, `pkg/lambda/watchdog/src/handler.ts`, `pkg/lambda/health-check/src/{handler,engine}.ts`, `pkg/web/src/hooks/use-game-actions.hook.ts` (rows 7, 14, 19, 20, 57–59).
4. **discord-interaction-stream** — A slash command travels Discord → CloudFront → interactions → followup → `PENDING#taskArn` → PATCH, fed by config rows and secrets the app writes; covering ~45 files incl. `pkg/lambda/interactions/src/handler.ts`, `pkg/lambda/followup/src/handler.ts`, `pkg/shared/src/canRun.ts`, `pkg/shared/src/ddb/{configStore,pendingStore}.ts`, `pkg/desktop-main/src/services/DiscordConfigService.ts`, `pkg/web/src/pages/discord/discord.page.tsx`, `pkg/infra/src/discordDomain.ts` (rows 55, 56, 62–65, 53).
5. **credential-and-secret-custody** — Where AWS keys, passphrases and health-check credentials are held, handed to SDK clients or the engine, rotated and redacted; covering ~45 files incl. `pkg/desktop-main/src/services/awsCredentialSource.ts`, `ElectronStoreService.ts`, `SafeStorageService.ts`, `PulumiCredentialResolver.ts`, `GuidedIamService.ts`, `AwsProfileService.ts`, `IamCheckService.ts`, `pkg/shared/src/iamPolicy.ts`, `pkg/shared/src/secrets/secretsStore.ts` (rows 72–76, 41, 64 partly, 29).
6. **file-bytes-into-volumes** — Local files reach an EFS volume through a throwaway helper task or the seeder Lambda; covering ~55 files incl. `pkg/desktop-main/src/services/FolderUploadService.ts`, `FileManagerService.ts`, `services/folderUpload/uploadEngine.ts`, `pkg/web/src/components/folder-upload/folder-upload-card.component.tsx`, `pkg/lambda/efs-seeder/src/handler.ts`, `pkg/infra/src/efs.ts` (rows 9, 13, 22, 23, 26, 60).
7. **operator-telemetry-readback** — Logs, diagnostics, cost estimates and audit entries flow back from AWS/local files into the operator's screen; covering ~65 files incl. `pkg/desktop-main/src/services/LogsService.ts`, `pkg/web/src/hooks/use-log-tail.hook.ts`, `DiagnosticsService.ts`, `DiagnosticsBundleService.ts`, `pkg/web/src/lib/report-renderer-error.utils.ts`, `CostService.ts`, `AuditService.ts`, `pkg/web/src/polling/polling-provider.component.tsx` (rows 4, 6, 21, 31–33, 45).
8. **first-run-provisioning-flow** — Wizard answers flow into electron-store, then into S3 buckets, a DynamoDB table, a seeded config and an initialised Pulumi stack; covering ~55 files incl. `pkg/web/src/components/first-run-wizard/first-run-wizard.component.tsx`, `pkg/desktop-main/src/controllers/wizard.controller.ts`, `FirstRunWizardService.ts`, `BootstrapService.ts`, `PulumiEngineService.ts`, `PulumiWorkspaceService.ts` (rows 66–71, 75, 40, 41).

**Pros**: Every chain in inventory §2 maps to exactly one cluster, so seams become cluster borders; it makes the "edit ≠ deploy" rule (clusters 1 vs 2) and "DNS is Lambda-managed" (cluster 3) structural; secrets get one home (cluster 5), matching the `redact before IPC` invariant. **Cons**: Shared stores are split by datum (`ElectronStoreService` is in 5 but also holds drafts (1) and folder selections (6)); `PulumiService` sits in 2 while its credential overlay is in 5 and stack init in 8; ~90 carrier files (preload, ipc bridge, ui primitives, electron entry, build/CI) have no datum and would form a tempting "transport" cluster — avoided here by leaving them as explicit *shared infrastructure* that each cluster declares a dependency on rather than as a cluster. **Best for**: reasoning about blast radius of schema changes and about where a value can leak (the `appliedGameServers` env-value echo, destroy output not redacted).

**Awkward boundary cases**: `DeploymentConfigService` (1) is also the restore step of rollback (2) and the projectName source for Lambda log groups (7). `GamesWriteService` (1) performs the health-check secret upsert (5). `ConfigService` caches stack outputs (2) but resolves region/bucket for every cluster. `infra/src/lambdas.ts` defines watchdog env (3), Discord Function URL (4) and seeder functions (6). `update-dns` (3) also PATCHes the Discord interaction (4). `BootstrapService` (8) seeds `deployment-config.json` (1) and the runs table (2). The polling registry (7) drives status for (3).

**OpenSpec distribution**: 1 ← game-draft-persistence, game-environment-variables, game-https-configuration, game-port-visibility, game-resource-picker, env-token-interpolation (validator half), pulumi-infra-program (config model half). 2 ← iac-plan-apply-page, iac-destroy-flow, iac-rollback, iac-run-history, pulumi-engine-runtime, pulumi-infra-program (program half), orchestrator-integration-coverage, in-task-tls-termination (infra half), lambda-runtime-currency. 3 ← game-health-checks (verdict half), in-task-tls-termination (DNS lifecycle requirement), cost-visibility (tag propagation). 4 ← none (gap). 5 ← aws-credentials, guided-iam-provisioning, aws-cloud-health, cloud-bootstrap (IAM simulation requirement), game-health-checks (credential requirements). 6 ← game-volume-folder-upload. 7 ← app-diagnostics-logging, infra-log-viewer, cost-visibility (estimate half). 8 ← wizard-flow, cloud-bootstrap (bucket/table requirements), guided-region-selection. Unassigned carrier/meta specs: custom-title-bar, desktop-only-operator-surface, preload-bridge-naming, app-icon, auto-update-scaffold, release-automation, node-toolchain-version, install-and-signing-docs, operator-documentation, docs-screenshot-capture (10 of 36).

**OpenSpec distribution**: 1 ← wizard-flow, guided-iam-provisioning, guided-region-selection, aws-credentials, cloud-bootstrap, aws-cloud-health. 2 ← game-draft-persistence, game-environment-variables, game-https-configuration, game-port-visibility, game-resource-picker, env-token-interpolation. 3 ← iac-plan-apply-page, iac-destroy-flow, iac-rollback, iac-run-history, pulumi-engine-runtime, pulumi-infra-program, orchestrator-integration-coverage, in-task-tls-termination, lambda-runtime-currency. 4 ← game-health-checks, cost-visibility, infra-log-viewer. 5 ← none (gap). 6 ← game-volume-folder-upload. 7 ← app-diagnostics-logging, auto-update-scaffold, custom-title-bar, desktop-only-operator-surface (UI-integrity requirements), preload-bridge-naming. 8 ← release-automation, node-toolchain-version, app-icon, install-and-signing-docs, operator-documentation, docs-screenshot-capture, desktop-only-operator-surface (harness requirements).

## Clustering C: Domain concept — the project's own nouns

**Pros**: Names already appear in module names, stack outputs and CLAUDE.md invariants, so arrows read naturally; cost-model invariants map cleanly (no ECS Service → 6; DNS Lambda-managed → 6; watchdog tags → 5; single source of truth → 2). **Cons**: `game-server` (1) and `deployment-config` (2) are tightly coupled (one is the map entry of the other) and will exchange files constantly; `stack` (4) absorbs `ConfigService` and much of infra, overlapping `run` (3) on `PulumiService`; the cost estimate, polling registry and the test tiers have no noun and fall into 6/12/residue. **Best for**: the OpenSpec → LID migration, since most capability names are already domain nouns.

**Awkward boundary cases**: `PulumiService.ts` is split between run (apply gates, records) and stack (preview/up/destroy mechanics) — assign to stack, cite from run. `infra/src/lambdas.ts` touches 5, 6, 7 and 8 — assign to stack with per-function cross-refs. `GamesWriteService` is deployment-config (writes) but performs health-check secret upsert (5). `escapes.ts` seeds Discord rows (7) and invokes seeders (8) — assigned to stack. `costs.page`/`CostService` have no noun; placed with task-and-dns (6) because the estimate is derived from the task definition. `electron-store` (`ElectronStoreService`) is shared by 9 (credentials), 2 (draft), 8 (selection), 4 (lock records) — assigned to wizard-and-bootstrap because credential custody is its heaviest duty.

**OpenSpec distribution**: 1 ← game-environment-variables, game-https-configuration, game-port-visibility, game-resource-picker, env-token-interpolation, in-task-tls-termination. 2 ← game-draft-persistence, pulumi-infra-program (config requirements), iac-rollback (restore requirement). 3 ← iac-plan-apply-page, iac-destroy-flow, iac-rollback, iac-run-history, orchestrator-integration-coverage. 4 ← pulumi-engine-runtime, pulumi-infra-program, lambda-runtime-currency. 5 ← game-health-checks. 6 ← cost-visibility. 7 ← none (gap). 8 ← game-volume-folder-upload. 9 ← wizard-flow, guided-iam-provisioning, guided-region-selection, aws-credentials, cloud-bootstrap, aws-cloud-health. 10 ← app-diagnostics-logging, infra-log-viewer. 11 ← auto-update-scaffold, release-automation. 12 ← custom-title-bar, preload-bridge-naming, desktop-only-operator-surface, app-icon. ## Clustering D: Behavioural boundaries — where coordinated state changes live

**Lens**: Group code by the state machine it advances: a cluster is the set of files that must agree on one lifecycle's states, transitions and guards.

**Clusters it produces** (10):

1. **iac-run-lifecycle** — idle → previewing → awaiting_approval → approved (15 min) → applying (pre-flight marker, durable lock) → success | failed | aborted | partialApply, plus the two lock machines (DynamoDB run lock, S3 backend lock) and their token-gated clears; covering ~65 files incl. `pkg/desktop-main/src/services/PulumiService.ts`, `RunService.ts`, `RunRecordService.ts`, `LockClearConfirmationGate.ts`, `PulumiLockRecovery.ts`, `PulumiCancellation.ts`, `controllers/{iac,iac-runs}.controller.ts`, `pkg/cloud-aws/src/AwsRunRecordStore.ts`, `pkg/shared/src/runs.ts`, `pkg/web/src/hooks/use-iac-run.hook.ts`, `pages/iac.page.tsx`, `components/submission-banners.component.tsx` (rows 34–39, 42–44).

## Clustering E: Sources of truth and their guardians (counterweight)

**Lens**: Group code by the authoritative store it is allowed to write and the readers that trust it — the way CLAUDE.md states its invariants ("`DeploymentConfig.gameServers` is the single source of truth", "DNS records are Lambda-managed", "watchdog state lives in ECS task tags").

## Where the sweeps disagreed (and how each lens must handle it)

- **Health-check Lambda** (sweep-8: cannot initialise; sweep-10 docs/spec: works) — every lens places it with the watchdog; the arrow must record the discrepancy as an Open Question rather than a behaviour.
- **`partialApply` durability** (sweep-7 store drops it; sweeps 3/5/10 assume it) — lenses D1 and E4 make this a transition/ledger defect; A2/B3/C3 would bury it inside a large cluster.
- **Durable run lock before first apply** (sweep-5 vs sweep-6) — only E4 ("who writes the ledger and when") and D1 expose it.
- **Region of truth** (sweep-4 `EcsService.ts:71` vs `:213`; sweep-6 store resolvers) — surfaced only by E2/E3; invisible in B and C.
- **Discord without a capability** — A4/B5/C7/D5 each create one cluster for it; E splits it across 4 (config rows), 5 (secrets) and 3 (followup RunTask), which is faithful to ownership but hostile to documenting the bot as one thing.
