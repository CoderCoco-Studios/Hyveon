## Why

The repo does not have one answer to "what Node version do I need?" — it has four. The app CI workflows (`test`, `lint`, `e2e`, `integration`, `package`) run Node 24; the two docs workflows (`docs-build`, `docusaurus-gh-pages`) run Node 20; and the three `engines.node` fields disagree with both and with each other (root `>=22.12.0`, `docs/` `>=18.0`, `scripts/` `>=20`). Nothing enforces any of them, so a contributor's local Node version depends on which directory they happened to read, and a docs build that passes locally on 24 is not the build CI runs on 20.

Docusaurus is a second, smaller version drift: `docs/` sits on 3.6.3 while 3.10.2 is current. It is not broken — 3.6.3 builds cleanly under Node 24 — but a four-minor gap on the tool that publishes the public site is worth closing while the docs toolchain is already being touched, and Docusaurus 3.10.2's own floor (`engines.node >=20`) is comfortably satisfied by the new pin.

## What Changes

- Both docs workflows move from `node-version: 20` to `'24'`, matching the five app workflows that already run 24. Every CI job in the repo then runs the same Node major.
- **BREAKING** (for contributor environments, not for runtime behaviour): `engines.node` becomes `>=24.0.0` in the root `package.json`, `docs/package.json`, and `scripts/package.json`. Anyone on Node 20 or 22 gets an `EBADENGINE` warning on install and must upgrade. No published artifact changes — the Electron app bundles its own Node, and the Lambdas run AWS's.
- Docusaurus and its five sibling packages (`@docusaurus/core`, `preset-classic`, `theme-mermaid`, `module-type-aliases`, `tsconfig`, `types`) go from 3.6.3 to 3.10.2, pinned exactly as the repo already pins them, with `docs/package-lock.json` regenerated. React stays on 18 — `@docusaurus/core@3.10.2` peers `^18.0.0 || ^19.0.0`.
- Every document that states a Node version is corrected to say 24: the `docs/docs/setup.md` prerequisites table, the two docs-workflow rows in `docs/docs/guides/maintainer.md` that currently say "Node 20", and both the prose and the example workflow in `docs/docs/guides/submodule.md`.
- Explicitly unchanged: the `runtime = "nodejs20.x"` setting on all five Lambdas in `terraform/aws/` and the matching `target: 'node20'` in the five `app/packages/lambda/*/esbuild.config.mjs` files. Those track the AWS Lambda runtime, not the developer toolchain; they must move together with a deploy, and they get their own change.

## Capabilities

### New Capabilities

- `node-toolchain-version`: the repo declares exactly one supported Node major for development and CI, and every place that states or enforces a version — `engines.node` in all three manifests, the `node-version` input of all seven workflows, and the setup/maintainer/submodule docs — agrees with it. Includes the rule that AWS Lambda runtime versions are governed separately and are not required to match.

### Modified Capabilities

None. No existing capability in `openspec/specs/` states a Node version or a docs-toolchain requirement, so there are no requirement deltas — this introduces a rule where there was none rather than changing an existing one.

## Impact

- **CI**: `.github/workflows/docs-build.yml`, `.github/workflows/docusaurus-gh-pages.yml`. The gh-pages workflow publishes the live site, so the first run after merge is the real proof the upgrade holds.
- **Manifests**: `package.json` (root), `docs/package.json`, `scripts/package.json`, `docs/package-lock.json` (regenerated by the Docusaurus bump).
- **Docs**: `docs/docs/setup.md`, `docs/docs/guides/maintainer.md`, `docs/docs/guides/submodule.md`.
- **Contributors**: anyone on Node < 24 must upgrade. There is no `.nvmrc` in the repo today, so the `engines` fields and this spec are the only statement of the requirement.
- **Not affected**: no application code, no test, no Terraform resource, and no AWS runtime. The app CI matrix is already on 24 and is left untouched.
