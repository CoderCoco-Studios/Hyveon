## ADDED Requirements

### Requirement: One supported Node major for development and CI
The repository SHALL declare exactly one supported Node.js major version for local development and continuous integration. That version is Node 24. Every place in the repository that states or enforces a Node version for developer tooling SHALL agree with it, so a contributor reading any one of them arrives at the same answer.

#### Scenario: Contributor reads the Node requirement from any manifest
- **WHEN** a contributor inspects `engines.node` in the root `package.json`, `docs/package.json`, or `scripts/package.json`
- **THEN** each one reads `>=24.0.0`
- **AND** none of them permits a Node major below 24

#### Scenario: Contributor installs on an older Node
- **WHEN** a contributor runs `npm install` in the repo root, `docs/`, or `scripts/` on Node 20 or Node 22
- **THEN** npm emits an `EBADENGINE` warning naming the `>=24.0.0` requirement

### Requirement: Every CI workflow runs the supported Node major
All GitHub Actions workflows that set up Node SHALL request the supported major — Node 24 — through `actions/setup-node`. No workflow SHALL pin a different major, so a build that passes locally on the supported version is the build CI runs.

#### Scenario: Docs workflows build the site
- **WHEN** `docs-build.yml` or `docusaurus-gh-pages.yml` runs
- **THEN** its `actions/setup-node` step requests `node-version: '24'`
- **AND** `npm ci && npm run build` in `docs/` completes successfully on that version

#### Scenario: Application workflows run tests and packaging
- **WHEN** `test.yml`, `lint.yml`, `e2e.yml`, `integration.yml`, or `package.yml` runs
- **THEN** its `actions/setup-node` step requests `node-version: '24'`

### Requirement: Documentation states the supported Node major
Every document that tells a reader which Node version to install, or which version a CI workflow runs on, SHALL state the supported major. A document SHALL NOT name a Node version that no manifest or workflow enforces.

#### Scenario: Operator reads the setup prerequisites
- **WHEN** an operator reads the prerequisites table in `docs/docs/setup.md`
- **THEN** the Node.js row requires Node 24 or newer, consistent with `engines.node`

#### Scenario: Maintainer reads the CI workflow reference
- **WHEN** a maintainer reads the workflow list in `docs/docs/guides/maintainer.md`
- **THEN** every entry, including the two docs workflows, states Node 24

#### Scenario: Parent-repo owner copies the example workflow
- **WHEN** someone copies the example GitHub Actions workflow from `docs/docs/guides/submodule.md`
- **THEN** its `node-version` is 24, matching the version the submodule's own CI uses

### Requirement: AWS Lambda runtime versions are governed separately
The Node version used by deployed AWS Lambda functions SHALL be governed independently of the development and CI toolchain version, and SHALL NOT be required to match it. The Lambda `runtime` declared in Terraform and the esbuild `target` used to bundle each Lambda SHALL stay consistent with each other, because the bundle's output syntax must be executable by the runtime that receives it.

#### Scenario: Toolchain Node version is raised
- **WHEN** the supported development and CI Node major is changed
- **THEN** the `runtime` values in `terraform/aws/*.tf` and the `target` values in `app/packages/lambda/*/esbuild.config.mjs` are left unchanged by that change
- **AND** raising them is treated as a separate, deploy-affecting change

#### Scenario: Lambda runtime version is raised
- **WHEN** the AWS Lambda runtime is moved to a newer Node version
- **THEN** the `runtime` in every Lambda's Terraform resource and the esbuild `target` in every Lambda's `esbuild.config.mjs` are updated together in the same change

### Requirement: Documentation toolchain tracks a current Docusaurus release
The documentation site SHALL be built with a Docusaurus release that is current at the time of the change, with `@docusaurus/core` and every sibling `@docusaurus/*` package held at the same exact version, and the lockfile regenerated by the package manager rather than hand-edited.

#### Scenario: Docusaurus packages are inspected
- **WHEN** `docs/package.json` is read
- **THEN** `@docusaurus/core`, `@docusaurus/preset-classic`, `@docusaurus/theme-mermaid`, `@docusaurus/module-type-aliases`, `@docusaurus/tsconfig`, and `@docusaurus/types` all specify the same exact version, with no range prefix
- **AND** that version satisfies its own `engines.node` under the supported Node major

#### Scenario: Site is built from a clean install
- **WHEN** `npm ci` followed by `npm run build` runs in `docs/` on the supported Node major
- **THEN** the build completes with `[SUCCESS] Generated static files`
- **AND** the rendered site still displays the navbar logo, the architecture SVG diagrams, and the mermaid diagrams
