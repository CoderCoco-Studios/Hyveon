## MODIFIED Requirements

### Requirement: Caddy TLS sidecar for HTTPS games

For every game with `https: true` in `DeploymentConfig.gameServers`, the ECS task definition MUST include a Caddy reverse-proxy sidecar container (official `caddy` image, version-pinned) exposing ports 443 and 80 and proxying to the game container's declared `webPort` over localhost. The sidecar MUST be generated by iterating `gameServers` in the Pulumi infra program (`defineEcs` in `app/packages/infra/src/ecs.ts`) — no hand-written per-game resources — and MUST be marked `essential` so a dead proxy stops the whole task instead of leaving an unreachable, billing task. Sidecar logs MUST stream to the game's existing CloudWatch log group under a distinct stream prefix. Task definitions of games with `https: false` MUST NOT contain the sidecar.

#### Scenario: HTTPS game task definition includes the sidecar

- **WHEN** an apply run provisions a game configured `https: true` with `webPort: 30000`
- **THEN** that game's task definition contains two containers: the game container (port mappings for `webPort` and any additional ports, unchanged mounts) and an essential Caddy sidecar with port mappings 443/tcp and 80/tcp reverse-proxying `{game}.{hosted_zone_name}` to `localhost:30000`, logging to `/ecs/{game}-server` with a `caddy` stream prefix

#### Scenario: Non-HTTPS game task definition is unchanged

- **WHEN** an apply run provisions a game configured `https: false` (or `https` omitted)
- **THEN** that game's task definition contains only the game container, with no Caddy sidecar, no 443/80 port mappings, and no cert volume

#### Scenario: Flipping https on a game requires only a config edit

- **WHEN** an operator sets `https: true` and a `webPort` on an existing game's config and applies
- **THEN** the sidecar container, cert access point, and security-group ingress all materialize without editing any other file in `app/packages/infra`

### Requirement: Security-group ingress for HTTPS games

The game-servers security group MUST allow public ingress on 443/tcp and 80/tcp when at least one HTTPS game exists (port 80 is required for the ACME HTTP-01 challenge and the HTTP-to-HTTPS redirect). An HTTPS game's `webPort` MUST NOT have ingress — the sidecar reaches it over localhost inside the task. An HTTPS game's additional `ports` entries MUST be ingressed like any other game's, honoring each entry's `visibility`. Non-HTTPS games' port ingress rules remain unchanged.

#### Scenario: HTTPS ports open, web port closed

- **WHEN** an apply run provisions at least one HTTPS game
- **THEN** the game-servers security group has 0.0.0.0/0 ingress on 443/tcp and 80/tcp, and no ingress rule exposing the HTTPS game's `webPort`

#### Scenario: Additional UDP port on an HTTPS game is reachable

- **WHEN** an HTTPS game declares `ports: [{ container: 30001, protocol: "udp" }]`
- **THEN** the game-servers security group has 0.0.0.0/0 ingress on 30001/udp

#### Scenario: No HTTPS games means no web ports

- **WHEN** an apply run provisions no HTTPS games
- **THEN** the game-servers security group contains no 443/80 ingress rules
