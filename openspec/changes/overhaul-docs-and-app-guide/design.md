## Context

The docs site is a Docusaurus 3.6.3 project in `docs/`, docs-only mode (`routeBasePath: '/'`),
published to GitHub Pages at `https://codercoco.github.io/Hyveon/` by
`.github/workflows/docusaurus-gh-pages.yml`. The sidebar is fully autogenerated
(`{type: 'autogenerated', dirName: '.'}`), so a new directory under `docs/docs/` with a
`_category_.json` becomes a sidebar section with no `sidebars.ts` edit.

Architecture diagrams are D2 sources in `docs/diagrams/` rendered by `docs/diagrams/render.sh`
into `docs/static/diagrams/*.svg`. Unusually, the rendered SVGs **are committed** even though
`docs/diagrams/README.md` claims they are gitignored — the `.gitignore` in that directory covers
`*.svg` in the *source* directory only, while `render.sh` writes elsewhere. This means the five
incorrect diagrams ship today and will keep shipping until the `.d2` sources are corrected and
re-rendered.

The application is an Electron desktop app with eleven renderer routes. Playwright already drives
it in CI through two projects: `chromium` (vite preview + `page.route()` stubs) and `electron`
(`_electron.launch()` against `out/main/index.js` with `HYVEON_TEST_MODE=1`, which activates the
`window.hyveon.__test.mock(channel, handler)` seam in the preload). Page objects under
`app/packages/web/e2e/pages/` already encapsulate navigation for both tiers. Playwright 1.59.1,
its Chromium build, and Electron 36.9.5 are all installed locally, and WSLg provides a display;
CI uses `xvfb-run -a`.

Three constraints shape the harness design:

1. Under Electron the renderer is loaded with `win.loadFile()`, so the origin is `file://` and
   `page.goto('/costs')` does not work. Existing specs navigate by clicking sidebar links or by
   `history.pushState` + a synthetic `popstate`.
2. `applyHyveonMocks` — the shared Electron stub helper — seeds only eight channels and returns
   `games.list` as `{ games: string[] }`, which contradicts the real
   `{ games: GameListEntry[] }` contract. Two existing specs already override it.
3. Async generators cannot cross the `contextBridge` (they fail with "An object could not be
   cloned"), so a mocked `terraform.runs.logs` or `logs.stream` cannot stream chunks into the UI
   from a `__test.mock` handler.

## Goals / Non-Goals

**Goals:**

- A "Using the app" documentation section that lets a new operator go from first launch to a
  running game server without reading source code.
- Screenshots that can be regenerated on demand by a single command, so they age with the UI
  instead of rotting.
- Documentation that contains no statement contradicted by the codebase, enforced going forward
  by a docs build that fails on broken links.
- An app whose chrome does not need an apology in its own user guide.

**Non-Goals:**

- Real player counts on the game card. That needs per-game server-protocol queries (Minecraft
  ping, Steam A2S, and so on) and belongs in its own change.
- Visual-regression testing. The harness produces documentation assets; it does not assert on
  them.
- Running the screenshot harness in CI. It needs a display, adds minutes to every run, and would
  turn any intentional UI change into a red build. It stays a maintainer command.
- Implementing the three placeholder screens (Servers, Metrics, Alerts). They are removed from
  the nav, not built.
- Rewriting `docs/docs/setup.md` structurally. It survived the audit largely intact; it gets
  targeted corrections only.

## Decisions

### Capture from Electron, not Chromium

The `electron` project renders the actual shipped product: real window chrome, real preload
bridge, real 1200×800 desktop layout. The `chromium` project renders the same React tree in a
browser tab — the wrong artifact for a desktop-app install guide, with browser scrollbars and no
window frame. Chromium also cannot render `/terraform`, `/terraform/history`, or
`/terraform/history/:runId` at all, because `hyveon-http-bridge.ts` has no `terraform` namespace.

*Alternative considered:* extend the HTTP bridge with a terraform namespace and capture from
Chromium. Rejected — more code, and it still produces browser-tab images.

### A separate Playwright config, not a spec in `e2e/specs/`

`playwright.config.ts` sets `testDir: './e2e/specs'`, so any spec dropped there runs in every CI
e2e job. A new `playwright.screenshots.config.ts` with `testDir: './e2e/screenshots'` keeps the
harness out of `npm run app:test:e2e` entirely, with no `testIgnore` bookkeeping in the main
config.

*Alternative considered:* a `screenshots` project inside the existing config with a grep filter.
Rejected — the exclusion becomes a negative constraint that a future contributor can silently
break.

### Navigate with the existing page objects, keep `file://`

Reuse the `gotoViaSidebar()` / `pushState`+`popstate` helpers the Electron specs already use, and
add equivalents for the routes that lack them. This keeps the harness on the same loading path as
the shipped app.

*Alternative considered:* launch with `ELECTRON_RENDERER_URL=http://localhost:4173` alongside
`vite preview`, giving the renderer an `http://` origin so `page.goto('/costs')` works. Simpler
navigation, but it introduces a second server process, diverges from the production load path,
and the main config deliberately strips that variable. The navigation problem is already solved;
paying for a server to re-solve it is a bad trade.

### One demo fixture module, not per-spec inline mocks

`e2e/screenshots/demo-data.ts` owns a `seedDemo(win)` that installs every channel the captured
screens touch, with realistic content (a running `minecraft` with a hostname, a stopped
`valheim`, a running `palworld`). It does **not** call `applyHyveonMocks`; it supersedes it, so
the `games.list` shape bug cannot leak in. Fixtures are typed against the shared contract types,
so a contract change breaks the build rather than producing a silently-wrong screenshot.

### Determinism: fixed clock, disabled animations, explicit window size

Three sources of run-to-run drift, each pinned:

- **Time.** The dashboard, costs, logs, audit, and polling indicator all render relative or
  absolute times. Fix the clock before navigation so "Updated 3s ago" and date axis labels are
  stable.
- **Animation.** Pulsing status dots, the spinning refresh icon, and Radix dialog transitions can
  each be caught mid-frame. Capture with `animations: 'disabled'` and inject a
  `* { transition: none !important; animation: none !important }` style tag.
- **Window size.** `page.setViewportSize()` is a no-op for Electron pages. Set the content size
  through `app.evaluate(({BrowserWindow}) => …setContentSize(1200, 800))` so the image dimensions
  do not depend on the host window manager.

Device scale factor stays at 1 for the first pass. `--force-device-scale-factor=2` would give
crisper images at 4× the file size; revisit if the images look soft on the published site.

### The streaming log screens get static screenshots

The contextBridge async-generator limitation means a mocked `terraform.runs.logs` cannot push
chunks. Two screens are affected:

- **Logs** — `logs.get` returns the initial snapshot synchronously and renders it, so a populated
  screenshot is achievable from the snapshot alone. Mock `logs.stream` as a no-op.
- **Terraform run output** — the ANSI log viewer cannot be populated through the mock seam.
  Capture the terraform page in its pre-run and awaiting-approval states, which are the states the
  documentation needs anyway (the operator needs to recognise the Approve gate, not admire log
  output). Document the limitation in a comment in the harness so a future contributor does not
  waste time on it.

### Documentation structure: one page per screen

A single long operator guide would put ten screenshots on one page and make the sidebar useless
for finding "how do I roll back an apply". One page per screen matches how an operator actually
searches, keeps each page short enough to read, and localises the screenshot for that screen next
to the text describing it. `docs/docs/app/index.md` carries the guided tour that stitches the
pages into a workflow.

`guides/user.md` keeps only what is genuinely not about the desktop app — the Discord slash
commands and what players experience — and links into the new section for everything else.

### `onBrokenLinks: 'throw'` lands with the content, not after

Flipping the flag first would fail the build on links this change is about to fix. Flipping it
last would leave a window in which a broken link merges. It changes in the same commit as the
final content pass, with a full `npm run build` in `docs/` as the gate.

### UI fixes are minimal and test-covered

Each of the four code changes is a deletion or a small addition:

- Costs joins the sidebar's Monitoring section, next to Dashboard and Logs.
- `logs.page.tsx` reads `location.state?.game` on mount and uses it as the initial selection when
  present, falling back to the first game otherwise. The `<Link state={{ game }}>` already exists
  on the card.
- The `readOnly`/`aria-hidden` search input and the three `aria-disabled` nav entries are deleted.
- The Players tile is deleted from the game card's stat grid, leaving a 3-item grid.

Existing specs and page objects that assert on the removed elements are updated in the same
change. Each behavioural fix gets a unit test; the nav change also gets an e2e assertion.

## Risks / Trade-offs

- **Screenshots go stale silently.** No CI check compares committed images against the live UI. →
  The maintainer guide states when to refresh, and the harness is a single command, so refreshing
  is cheap. A CI freshness gate was considered and rejected as flake surface; it can be added
  later without changing the harness.
- **`onBrokenLinks: 'throw'` breaks the docs build on an unrelated future PR.** → That is the
  point; a dead link should be a build failure. The risk is a contributor blocked by a link they
  did not write, mitigated by fixing every existing broken link in this change and by the error
  message naming the offending file.
- **Regenerating the SVGs requires `d2` on the machine running `render.sh`.** → CI already
  installs and runs it in `docusaurus-gh-pages.yml`. If `d2` is unavailable locally, the corrected
  `.d2` sources still land and CI re-renders; the committed SVGs must be regenerated before merge
  either way, since they are the artifacts that actually ship.
- **The demo fixtures drift from the real IPC contracts.** → Fixtures are typed against the shared
  contract types rather than declared inline, so a contract change fails type-checking.
- **Removing the disabled nav entries removes a roadmap signal.** Operators lose the hint that
  Metrics and Alerts are planned. → A disabled control is a worse signal than no control; the
  roadmap belongs in the repository, not in dead chrome.
- **The change is large and spans docs, test tooling, and app code.** → It is sequenced so the
  app fixes land first (they alter what the screenshots must show), then the harness, then the
  content that embeds the output. Reviewing in that order keeps each stage self-contained.

## Migration Plan

1. **App fixes first.** Nav, logs preselection, chrome cleanup, Players removal, plus the test
   updates. Independently mergeable and independently verifiable.
2. **Harness second.** Config, demo fixtures, capture spec. Verified by running it and inspecting
   the produced PNGs.
3. **Diagram sources third.** Correct the `.d2` files, re-render, confirm the committed SVGs
   changed.
4. **Content last.** New `docs/docs/app/` section embedding the captured images, the accuracy
   sweep across existing pages, `guides/user.md` reduction, `docs/diagrams/README.md` rewrite,
   then the `onBrokenLinks` flip gated on a clean `npm run build` in `docs/`.

Rollback is per-stage: each stage is a coherent set of files with no runtime coupling to the
others. Reverting the content stage leaves a working harness and a working app; reverting the app
stage requires re-running the harness to refresh three affected screenshots.

## Open Questions

None blocking. Two deferred decisions, both revisitable without rework:

- Whether to raise the capture device scale factor to 2 once the images are visible on the
  published site.
- Whether a CI freshness check for screenshots is worth its flake cost once the harness has
  proven stable across a few UI changes.
